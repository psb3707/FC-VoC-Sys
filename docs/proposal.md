## 1. 배경

설계사(FC)의 영업은 영업지원시스템(SFA) 위에서 이뤄진다. 시스템 오류는 곧 청약 중단과 고객 상담 지연으로 이어진다. 그런데 현재 오류 대응은 사람 사이의 구두 전달에 의존하고 있어, 문제가 생겨도 근본적으로 해결되지 않고 현장으로 경과가 돌아오지 않는다.

동시에 회사는 큰 변화를 앞두고 있다.

- **영업채널 통합:** 두 회사 설계사가 하나의 시스템을 쓰게 되면서 전환기 문의가 급증할 수 있다.
- **신규 SFA 구축:** AI FC, 음성·자연어 메뉴, 자동 통역 등 AI 기능 도입이 예정되어 있다.
- **AI 코딩 에이전트 PoC:** 개발·테스트 업무에 적용을 검증 중이며, 신규 SFA 구축에도 활용을 검토하고 있다.

이 제안은 지금의 오류 대응 구조를 AI·디지털로 개선하고, 이를 신규 SFA와 코딩 에이전트로 이어지는 체계의 출발점으로 삼는 것을 목표로 한다.

## 2. 현황

### 2.1 현재 오류 문의 흐름 (확인됨: 멘토 면담, 부지점장 1인 답변)

```
설계사 ──▶ 지점장·부지점장 (가장 먼저 찾는 창구)
              ├──▶ 영업관리자 단톡방
              └──▶ 영업팀에 직접 연락 (전화·메신저)
                        └──▶ 영업팀(현업) 1차 처리 ──(필요 시)──▶ IT부서

회신: 영업팀 → 관리자 → 설계사 = 임시방편(쿠키 삭제 후 재접속 등), 경과 공유 없음
900 헬프데스크: 존재하지만 현장 답변에서 언급되지 않음
```

영업팀이 1차로 처리하고 필요하면 IT가 합류한다. 회신은 주로 쿠키 삭제 후 재접속 같은 임시방편이고, 근본 해결 여부와 경과는 공유되지 않는다.

### 2.2 현장에서 보고된 결함 사례 (확인됨)

| 사례 | 내용 | 영향 |
| --- | --- | --- |
| 알림톡 링크 오연결 | 세미나 초대장 발송 이력이 있는 FC가 청약 서명 알림톡을 누르면 초대장으로 연결됨 | 청약 진행 중단. 전자서명 절차의 신뢰성과 완전판매 측면의 리스크로 볼 수 있어 준법 부서 확인이 필요 |
| 로그인 입력 오류 | 문자는 b, 숫자는 1만 입력됨 | 시스템 접속 불가 |
| 고객 목록 클릭 오류 | 상세 조회를 위해 이름이 아닌 성별을 눌러야 함 | 매일 반복되는 사용 불편 |

세 사례 모두 사용법 안내로는 해결되지 않는, 코드 수정이 필요한 실제 결함이다.

### 2.3 SFA에 이미 있는 지원 창구 (확인됨: SFA 메인 화면, 멘토 답변)

SFA 메인 화면에는 지원 창구가 여럿 있지만, 결함을 접수하고 추적하는 창구는 없다. 현장 답변에서도 이 창구들은 언급되지 않았다.

| 창구 | 위치 | 하는 일 | 결함 대응과의 관계 |
| --- | --- | --- | --- |
| 챗봇 | 오른쪽 퀵메뉴 | 정해진 시나리오의 업무 안내와 FAQ만 응답 | 자유로운 오류 설명을 받거나 결함으로 등록할 수 없음 |
| 원격지원·원격요청 | 상단, 오른쪽 퀵메뉴 | 설계사 화면을 헬프데스크에 미러링해 오류 화면을 직접 확인 | 확인 수단은 있으나 자주 쓰이지 않음. 확인 결과가 결함으로 기록·이관되는지는 확인 필요 |
| 제보 | 상단 | 보험사기(허위 청구) 신고 | 무관. 새 기능의 이름이 이와 겹치지 않도록 주의 |
| 시스템공지 탭 | 메인 가운데 | 시스템 관련 공지 | "알려진 오류" 안내를 붙일 수 있는 자리 |

### 2.4 SFA 메인 화면 구성 (목업 배경 참고)

- 상단: 업무 메뉴(고객관리, 활동관리, DB관리, 계약관리, 재무설계, 가입설계, 청약, 영업관리, 지식관리, 관리자)와 유틸리티(제보, 원격지원, 수수료규정, 메뉴검색, 약관검색, 스케줄, 알림, 로그아웃)
- 왼쪽: 사용자 정보, 실적 카드(건수, 환산초회P), 활동량·고객 현황 카드
- 가운데: 날짜별 일정 카드, 이번 달 생일·보험만기·납입만기·콜센터접촉 요약, 탭(가입설계 이력, 청약진행현황, 신계약보완, 해피콜보완, 계약문서열람), 공지 탭(일반공지, 시스템공지, CEO 메시지, 영업자료실)
- 오른쪽: 큰 버튼 형태의 퀵메뉴(신규고객동의, 기존고객동의, 고객종합조회, 가입설계, 상세 보장분석, 교육방송, UW 매뉴얼, 챗봇, 원격요청 등)

## 3. 문제 정의

> 설계사가 겪는 시스템 결함은 관리자를 거쳐 구두로 전달되고, 임시방편으로 종결되며, 경과가 현장에 공유되지 않는다. SFA에는 사용법 안내용 시나리오 챗봇과 화면 확인용 원격지원은 있지만, 자유로운 오류 설명을 받아 결함으로 등록하고 추적하는 창구는 없다. 문제는 창구의 부재가 아니라, 확인과 해결 사이의 단절이다.

| 핵심 문제 | 현상 | 영향 |
| --- | --- | --- |
| 근본 해결 부재 | 쿠키 삭제·재접속 같은 임시방편으로 종결 | 같은 결함 반복, 현장 불신 |
| 경과 공유 부재 | 근본 해결 준비 여부와 진행 상황이 공유되지 않음 | 관리자가 매번 연락해 확인 |
| 결함 이력 미관리 | 문의가 단톡방·전화로 흩어지고, 전달 과정에서 재현 정보가 빠짐 | 영향 범위와 원인 파악 불가 |
| 현장 대응 부담 | 관리자가 고령 FC를 일일이 찾아가 해결, 지점 밖 문의는 대응이 어려움 | 관리자 업무 부담, 영업 중단 |

### 구조적 원인

- 문의를 "응대"로만 처리하고 "결함"으로 등록·추적하는 체계가 없다.
- 확인 수단(원격지원)으로 알게 된 내용도 결함 기록과 개발 이관으로 이어지지 않는 것으로 보인다(확인 필요).
- 영업팀이 받은 결함이 IT 개발로 넘어가는 기준이 "경중"이라는 판단에 의존한다.
- 누가, 언제 현장에 경과를 알릴지 정해져 있지 않다.
- 고령 FC가 스스로 하기 어려운 안내가 많고, 지점 밖에서 도움받을 수단이 없다.

### 근본 수정이 안 되는 이유 (가설, 확인 필요)

| 원인 가설 | 확인 방법 | 해결책의 무게중심 |
| --- | --- | --- |
| A. 결함 관리·이관 체계가 없다 | 결함이 개발로 넘어가는 기준과 기록이 있는지 질문 | 결함을 수정 단계로 연결 |
| B. 수정 여력이 없거나 신규 SFA 교체를 앞두고 우선순위가 밀렸다 | 현행 시스템 유지보수 계약 범위, 수정 동결 여부 질문 | 투명한 경과 공유와 결함 목록의 신규 SFA 요구사항 이관 |
| C. IT가 결함 자체를 모른다 | 현장 사례 3건이 IT에 알려져 있는지 대조 | 전달 경로와 재현 정보 보강 |

세 경우 모두 결함을 정확히 기록하고 현장에 경과를 알리는 체계는 필요하다. 다만 기대효과는 원인에 따라 다르게 제시한다(6장 참고). 또한 청약·서명 절차를 막는 결함은 단순 불편이 아니라 컴플라이언스와 연결될 수 있으므로, 우선순위를 가장 높게 둔다.

## 4. AI/디지털 기반 해결책 도출

제안하는 해결책은 **현장 결함 해결 순환 체계**다. 접수에서 끝내지 않고, 결함이 처리되고 그 경과가 현장으로 돌아올 때까지 하나의 고리로 관리한다.

### 4.1 제안 구조 (TO-BE)

```
[SFA 메인 화면 — 설계사·관리자]              [SFA 밖 — 영업팀·IT]

① 전산 오류 접수 ──────────────────────────────▶ ③ 결함 대장
   알려진 오류 먼저 보기      (이미 알려진 오류면      대표 결함으로 묶기
   업무·증상 선택 + 한 줄      "나도 겪었어요":        처리 등급·상태 관리
        │                    건수만 증가)                 │
        ▼                                               ▼
   ② AI 접수 도우미 ─────────────────────────────▶ ④ 처리
      되묻기·구조화                                  영업팀 임시조치
      사용법·결함 분류                               IT 원인 분석·수정 또는 보류 결정
      안내문 초안                                        │
                                                        │
⑤ 알려진 오류·내 신고 ◀── 묶인 신고자 전원에게 알림 ────┘
   상태 변경 시 자동 알림
   FC용 쉬운 안내문
```

### 4.2 해결 흐름

1. **접수:** SFA 메인 화면의 "전산 오류 접수" 버튼에서 시작한다. 먼저 같은 화면·증상의 알려진 오류를 보여주고, 이미 있으면 "나도 겪었어요"로 건수만 올린다. 없으면 업무와 증상을 선택하고 한 줄로 입력하며, AI가 로그로 알 수 없는 정보만 되묻는다. 관리자는 같은 화면에서 대리 접수한다.
2. **분류:** AI가 사용법 문의·결함·개선 요청을 나누고, 사용법 문의는 안내 후 종료한다. 결함은 규칙에 따라 처리 등급(즉시·일반·모아서)을 정한다.
3. **결함 대장:** 같은 원인의 신고를 대표 결함 하나로 묶고, 영향 지점 수와 상태를 관리한다.
4. **처리:** 영업팀이 임시조치를 안내하고, 등급에 따라 IT가 원인을 분석·수정한다. 고치지 않기로 한 결정(예: 신규 SFA에서 해결)도 정상 종결로 다룬다.
5. **경과 공유:** 대표 결함의 상태가 바뀌면 묶인 신고자 모두에게 자동으로 알린다. 안내문은 AI가 쉬운 말로 초안을 쓰고 담당자가 승인한다.

### 4.3 구조 원칙: 접수는 SFA 안, 관리는 SFA 밖

| 층 | 위치 | 이유 |
| --- | --- | --- |
| 접수 버튼·패널, 알려진 오류·내 신고 | SFA 메인 화면 안 | 고령 FC에게 익숙한 화면, 화면 정보 자동 첨부 |
| 결함 대장·처리 흐름 | SFA 밖 별도 화면 | SFA가 고장 나도 작동, 여러 시스템에 걸친 결함 기록, SFA 교체 후에도 이력 유지 |

### 4.4 AI를 쓰는 곳과 쓰지 않는 곳

| 기능 | 방식 | 이번 PoC |
| --- | --- | --- |
| 한 줄 입력을 결함 티켓으로 구조화 | AI | 포함 |
| 로그로 알 수 없는 재현 정보 되묻기 | AI | 포함 |
| 사용법·결함·개선 요청 분류 | AI | 포함 |
| FC용 쉬운 안내문 초안 | AI + 담당자 승인 | 포함 |
| 기기·화면·시각 등 기본 정보 | 자동 수집(로그) | 가상 값으로 시연 |
| 처리 등급·담당 부서 지정 | 규칙 | 포함 |
| 상태 관리·알림 발송 | 일반 자동화 | 화면 미리보기만 |
| 같은 결함 묶기 | AI 후보 추천 | 제외. PoC는 사람이 연결 |
| 화면 캡처 처리, 로그 연동 | 이미지 마스킹, 시스템 연계 | 제외 (후속 단계) |

**왜 AI인가:** 기존 챗봇은 정해진 시나리오만 따라가서 "알림톡을 누르면 초대장이 떠요" 같은 자유로운 오류 설명을 받을 수 없다. 반대로 양식만 두면 빈칸이 남는다(오픈소스 이슈 템플릿 준수율 약 30%). 그래서 정형 정보는 선택형과 자동 수집으로 받고, AI는 남은 빈칸을 되묻는 데 집중한다. 이 방식이 선택형 양식보다 실제로 나은지는 PoC에서 직접 비교한다. AI가 더 낫지 않다면 양식으로 가는 것이 맞다.

벤더 사례의 수치는 AI·업무 표준화·플랫폼 통합을 함께 도입한 결과라 AI 효과의 근거로 쓰지 않고, 구조가 타당하다는 근거로만 쓴다. 또한 AI가 빠진 재현 정보를 되묻는 방식의 효과를 직접 검증한 공개 사례는 찾지 못했다. 이번 PoC의 비교 검증이 그 빈칸을 직접 확인한다.

**이번 범위에서 제외:** 기존 챗봇·원격지원과의 연계는 이번 PoC에서 다루지 않는다. 설계사가 직접 쓰는 대화형 챗봇도 고령 FC의 사용 부담과, 결함은 즉답으로 해결되지 않는다는 점 때문에 제외했다.

### 6.2 원인별 기대효과 시나리오

| 시나리오 | 조건 | 기대효과 |
| --- | --- | --- |
| A. 체계 부재 | 결함이 개발로 넘어가는 기준과 기록이 없어서 수정이 안 됨 | 결함이 수정 단계로 연결되어 근본 수정 완료율 상승, 리드타임 단축, 재발률 감소 |
| B. 여력·우선순위 | 유지보수 여력 부족이나 신규 SFA 교체를 앞둔 수정 동결 | 수정이 어렵다는 사실과 대안을 투명하게 알려 관리자의 확인 연락 감소, 결함 목록을 신규 SFA 요구사항으로 넘겨 같은 결함의 재발 방지 |

어느 쪽이든 결함을 정확히 기록하고 현장에 알리는 체계의 가치는 남는다. 다만 B라면 "결함을 고치는 체계"가 아니라 "결함을 투명하게 관리하고 다음 시스템에서 반복되지 않게 하는 체계"로 제안의 성격을 바꿔 설명한다.

### 6.3 정성적 효과

- **관리자 부담 경감:** 결과를 쫓아다니며 확인하던 일이 줄고, FC에게 전달할 안내문을 바로 받을 수 있다.
- **컴플라이언스 리스크 조기 인지:** 청약·서명 절차에 영향을 주는 결함을 최우선으로 등록·이관해, 완전판매 관련 리스크를 늦지 않게 드러낸다.
- **개선 근거 확보:** 결함별 영향 범위와 반복 횟수가 데이터로 쌓여, 수정 우선순위의 근거가 된다.
- **신규 SFA에 재사용:** 화면·증상·재현 조건이 정리된 결함 기록은 신규 SFA의 요구사항과 테스트 시나리오로 그대로 쓸 수 있다.

### 7.2 운영 규칙 (AI가 아니라 규칙으로 구현)

- **처리 등급**
  - 즉시: 청약·서명을 막는 결함, 컴플라이언스 우려 → 바로 IT 이관
  - 일반: 로그인·접속, 여러 지점에서 반복 → 영업팀 임시조치 후 주간 검토
  - 모아서: 사용 불편, 개선 요청 → 월 단위 검토
- **상태 단계:** 접수 → 재현 확인 → 원인 파악 → 임시조치 → 수정 예정(예정일) → 해결. "수정하지 않음"(사유 필수: 신규 SFA에서 해결, 우회법으로 충분 등)도 정상 종결.
- **결함 대장 필드:** 유형(사용법/결함/개선), 대표 결함 ID, 신·구 시스템 구분, 영향 지점 수, 연결된 신고 목록, 처리 등급, 상태, 담당 부서
- **알림 원칙:** 의미 있는 상태 변경 때만 현장에 알린다. "확인 중" 알림을 반복하지 않는다. 상태는 대표 결함 단위로 한 번 바꾸고, 묶인 신고자 전원에게 전파한다.

### 7.3 접수 증가 대비

- 알려진 오류를 먼저 보여주고 "나도 겪었어요"로 건수만 올려 중복 신고를 흡수한다.
- 상태는 대표 결함 단위로 갱신하므로, 담당자 업무는 신고 건수가 아니라 결함 수만큼만 늘어난다.
- IT 처리 역량은 늘릴 수 없으므로 영향 지점 수 × 업무 중요도로 우선순위를 정한다.

### 7.4 개인정보·보안 원칙

- **원칙:** AI에게는 "누구"가 아니라 "어떤 상태"를 넘긴다. 고객이 누구인지는 사내 시스템 안에서 권한 있는 담당자만 확인한다.
- **AI 호출 전 규칙 기반 마스킹 (AI로 마스킹하지 않음)**
  - 주민등록번호, 계좌·카드번호 형식: 입력 자체를 차단
  - 이름, 전화번호, 주소: 마스킹
  - 증권번호·설계번호·고객번호: 참조키로 치환. 원래 값과의 매핑은 사내(서버 로컬)에만 보관
- **속성 전달:** 판단에 필요한 속성만 범주로 넘긴다(계약 상태, 상품군, 최근 변경 유형과 월, 청약 경로). 여러 속성 조합으로 특정인을 알아볼 수 없도록 날짜는 월 단위, 상품은 상품군 단위로 일반화한다.
- **고객 관련 오류:** "고객 관련 오류인가요?"를 먼저 묻고, 고객번호는 별도 입력란으로 받는다. 이 값은 AI로 보내지 않는다.
- 화면 이미지는 AI로 보내지 않는다. 모든 데이터는 가상이다.
- 외부 LLM API는 사전 승인 후 인터넷망 PC에서만 쓴다. LLM 호출부는 분리해 사내 승인 모델로 교체할 수 있게 한다.

### 7.5 고객 데이터 관련 오류 처리 예시

1. FC 입력: "홍길동 고객 가입내역이 안 보여요. 계약번호 1234…"
2. 마스킹: "[고객] 가입내역이 안 보여요. 계약 [참조키 K-01]"
3. 자동 수집: 화면(고객종합조회), 오류코드, 발생 시각
4. 속성 전달: 계약 상태 유지 / 상품군 종신 / 최근 변경 계약자 변경(이번 달) / 청약 경로 모바일
5. AI 판단: 데이터 반영 결함 가능성, 담당 계약관리 현업 + IT, 되묻기 "다른 고객도 같은 증상이 있나요?", FC 안내문 초안
6. 담당자: 참조키로 사내 시스템에서 실제 계약 확인
