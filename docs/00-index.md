## 3. 문서 우선순위
승인된 ADR > `docs/00~12` > 요청 프롬프트(원문) > `proposal.md`
(제안서 머리말: 요청 프롬프트와 다르면 요청 프롬프트 우선. 기준선 이후에는 정리된 문서가 판단 기준.)

## 4. 표기 규칙
- 요구사항 ID: `REQ-<영역>-<번호>` (영역: IN 접수, MD 모드, LG 대장, KN 알려진 오류·내 신고, NT 알림·안내문, AI, PV 개인정보, EX 실험, OP 운영, ST 통계, NF 비기능)
- 우선순위: **M** Must, **M\*** 사실상 Must(대장 최소판), **S** Should, **C** Could, **X** 제외
- **가정**(`[가정 G#]`)과 **미결**(`[미결 Q#]`)은 담당·기한을 함께 적는다.
- 확인 상태: 제안서의 "확인됨 / 가설 / 확인 필요" 구분을 유지한다.

## 5. 변경 절차
- 기준선(`docs-v1.0`) 이후 범위·구조·규칙 변경은 **ADR 작성 → 문서 수정 → 구현** 순서.
- 문구 수정 같은 사소한 변경은 커밋 메시지로 충분.
- 문서와 구현이 다르면 임의로 맞추지 않고 어느 쪽을 고칠지 결정해 기록.

## 6. 용어집
| 용어 | 뜻 |
|---|---|
| SFA | 영업지원시스템. 설계사가 쓰는 현행 업무 시스템 |
| FC | 설계사 |
| 신고 | FC(또는 관리자 대리)가 접수한 개별 오류 건 |
| 대표 결함 | 같은 원인의 신고 여러 건을 묶은 결함 단위. 상태는 여기서 관리 |
| 결함 대장 | SFA 밖의 대표 결함 관리 화면 |
| 알려진 오류 | 이미 등록·공개된 대표 결함. FC가 "나도 겪었어요"로 건수만 올림 |
| 되묻기 | AI가 자동 수집·선택으로 알 수 없는 재현 정보만 최대 3개 묻는 단계 |
| 참조키 | 증권·설계·고객번호를 치환한 값 (예: K-01) |
| 속성 전달 | 참조키로 가상 계약을 조회해 범주형 속성만 AI에 넘기는 방식 |
| A모드 / B모드 | A: 선택 항목 + 한 줄 입력 (AI 끔). B: A + AI 구조화·되묻기 |
| 칸(cell) | 실험 배정 4종 (모드 순서 × 세트 순서) |
| 마일스톤 | 일정 지표 (M1 문서 기준선 11/13, M2 화면 완료 11/19, M3 실험 전 구간 점검 12/2). 단계 전환의 승인 조건이 아님 |
