# ADR-027. 고객 동의 URL 키패드 오류를 대표 시연으로 더하고, 빠른 도움·간편 신고·FC별 현황으로 고친다

- 상태: 승인 (결정자: 사용자, 2026-11-21. "메인 시연 시나리오 전환 및 실사용 UX 개선 개발 지시서"의 Phase 1 검토 뒤 대화에서 승인)
- 바꿈: ADR-026 결정 1(되묻기를 모두 마친 뒤 결과를 보임 → 안내에 필요한 항목만 먼저 묻고 결과를 먼저 보임), ADR-026 결정 3(되묻기 상담의 행동 줄에 보조 버튼 [같은 오류로 간편 알리기] 추가, 주 버튼은 그대로 하나), ADR-026 결정 8(AI 문의가 안내한 사례라도 업무가 다르면 후보·근거에서 뺌), ADR-025 결정 6·REQ-KN-06(관리자 [지점 FC 문의]를 신고 건이 아니라 FC 단위로 묶고 업무 상황 4가지로 나눔)
- 확장: ADR-019(같은 오류 참여 `ME_TOO`에 상담에서 확인한 허용 코드를 붙임), ADR-026 결정 5·6(허용 코드에 새 발생 조건·임시조치 상태·추가 지원 필요 추가), ADR-025 결정 5(업무 재개 회신을 같은 값으로 다시 받아도 한 번만 기록)
- 유지: 사람이 대표 결함에 연결한다(REQ-LG-02, ADR-017). 임시조치 ≠ 해결, AI 추천 ≠ 같은 결함 확정, 접수 ≠ 담당자 확인. 자유 입력 원문은 페이지 메모리에만(ADR-021). 대리 접수자는 FC 대신 업무 재개를 정하지 않는다(ADR-026 결정 7). 기존 전자서명 시나리오(D-2026-001)와 그 검사는 남긴다.

## 배경
1. 대표 시연을 "고객이 상품소개동의 URL에서 본인확인 뒷자리 입력란을 누르면 숫자 키패드가 나타나지 않는 오류"로 바꾸려 한다. 이 오류는 원인·영향 기종·승인된 임시조치·실제 담당 부서가 **모두 미확정**이다. 지금 구조는 임시 방법이 있는 결함(D-2026-001)만 전제로 해서, 임시조치가 없을 때 FC에게 무엇을 보여 줄지 정해져 있지 않다.
2. 지금 AI 문의는 확인 항목을 모두 답해야 결과를 보인다. 고객이 기다리는 동안 안내에 필요 없는 질문이 도움을 늦춘다.
3. 상담 결과 `RESUMED / STILL / UNKNOWN`만으로는 "임시조치가 없음"과 "시도했지만 안 됨"을 구분할 수 없다. 임시조치가 없는 결함에서 "아직 안 돼요"를 고르면 시도하지 않은 조치의 실패가 기록될 수 있다.
4. 이미 알려진 결함과 같은 오류라고 FC가 확신해도 상담 뒤에 상세 접수밖에 길이 없다.
5. 확인 화면에서 업무·증상을 바꿔도 상담이 안내한 사례(`suggestedDefectId`)·시도한 조치가 남아, 다른 업무의 결함이 후보로 계속 추천될 수 있다.
6. 관리자 [지점 FC 문의]는 위에서는 FC 수를 세고 아래에서는 신고 건마다 FC를 되풀이한다. 임시조치가 없는 결함은 "임시 방법이 아직 없어요"만 보여, 지원이 필요한 FC를 찾기 어렵다.
7. 접수 완료 처리(`intake-quick.js finish`)는 업무 재개 기록에 실패하면 같은 함수를 다시 부르고, 기록 API도 같은 회신을 다시 받으면 후속 기록을 또 남긴다.

## 결정
1. **새 대표 결함과 업무 코드(가상).** 대표 결함 `D-2026-007` "고객 동의 URL에서 뒷자리 숫자 키패드가 열리지 않아요"를 더한다. 유형은 결함, 처리 등급은 즉시(02번 1절 판정 2: "동의" 키워드), 상태는 **접수**, 공개 대상, 임시 방법·FC 안내문·수정 예정일은 **없음**으로 둔다. 원인·영향 기종·OS·브라우저는 데이터에 넣지 않는다(미확정을 사실로 만들지 않음). 업무는 청약·서명과 나눠 새 코드 `CUSTOMER_CONSENT` "고객동의·본인확인", 대표 증상은 새 코드 `CANNOT_INPUT` "입력할 수 없어요(키패드가 안 떠요)"를 쓴다. 담당 부서는 **시연용 가상 매핑** "고객동의업무팀(가상)"으로 두고 실제 부서는 확인 필요로 남긴다. 서로 다른 가상 FC 3명의 신고 3건을 묶어 두고, 그중 1건은 관리자 박새벽(가상)과 같은 지점의 조은별(가상)이다. 대표 시연 FC는 신고 이력이 없는 새 가상 FC(같은 지점)다.
2. **새 발생 조건은 기존 조건과 따로 둔다.** `conditions`에 `INPUT_STEP`(앞자리 입력/뒷자리 입력/모름), `KEYPAD_SYMPTOM`(키패드가 안 나타남/키패드는 보이지만 입력 안 됨/모름), `DEVICE_OS`(Android/iOS/모름), `URL_PATH`(앱 안 브라우저/외부 브라우저/모름)를 더한다. 오류가 난 기기에 `OTHER` "다른 기기"를 더한다. `SEMINAR_HISTORY`는 이름을 바꾸지 않고 그대로 둔다. 허용 목록·표시 이름·출처 처리는 `IntakeFacts` 하나를 같이 쓴다.
3. **빠른 도움 순서(ADR-026 결정 1 변경).** 확인 항목마다 `stage`를 둔다: `guide`(대장의 안내를 고르는 데 필요한 항목)와 `report`(담당자 확인용 항목). 한 상담에서 묻는 항목은 지금처럼 **최대 3개**이고, 질문 문장에서 알 수 있는 항목은 묻지 않는다. 순서는 ① `guide` 항목 → ② 결과 카드(대장의 지금 상태·임시 방법) → ③ 결과 질문 → ④ `report` 항목 → 마침. `report` 항목은 모두 "잘 모르겠어요"로 넘길 수 있고, 묻는 중에도 [기다리지 않고 접수]가 있다. D-2026-001은 초대장 발송 이력만 `guide`, 기기·고객 대기는 `report`다. D-2026-007은 임시조치가 없어 `guide` 항목이 없다(바로 결과 카드).
4. **임시조치가 없을 때 안내(B).** 결과 카드는 "현재 확인된 임시조치가 없어요"와 "고객 동의 절차가 진행되지 않는 상황을 접수에 남길게요"를 보이고, 접힌 영역 **"사람의 도움을 받을 수 있는 경로"**에 이 시안에서 확인된 것만 적는다: 접수하면 담당 창구(가상 매핑)가 확인하고 알림·내 접수내역으로 알린다, 접수할 때 전화 연락을 요청할 수 있다, 이 화면에서 바로 전화·메신저로 연결하지는 않는다. 가상 전화 버튼·처리 보장 문구·우회 안내(본인확인을 건너뛰거나 개인정보를 다른 채널로 받기)는 만들지 않는다. 결과 질문은 "지금 이 고객님과 업무를 이어가기 어려운 상황인가요?"(네, 진행이 어려워요 / 아니요, 기다릴 수 있어요 / 잘 모르겠어요)이며 답은 `supportNeeded`가 된다.
5. **상태를 네 가지로 나눈다.** 접수 저장본에 `workaroundState`를 더한다: `NONE`(승인된 임시조치 없음) · `OFFERED`(안내했지만 결과 미확인) · `TRIED`(시도함). `workOutcome`은 그대로 두되 `TRIED`일 때만 `RESUMED|STILL`, `OFFERED`일 때만 `UNKNOWN`, `NONE`이면 항상 `null`이다. 시도한 조치 문장(`attemptedWorkaround`)도 `TRIED`일 때만 남는다. 허용 목록 검사(`IntakeFacts.clean`)가 어긋난 조합을 버리므로 **임시조치가 없는데 "아직 안 돼요"가 기록되는 일은 없다.** `supportNeeded`(`YES|NO|UNKNOWN`)는 업무 진행 어려움·추가 지원 필요 여부이며, 대리 접수에서는 업무 재개와 같은 이유로 저장하지 않는다. `workaroundState`가 없는 기존 저장본은 `workOutcome`으로 읽는다(`RESUMED|STILL` → `TRIED`, `UNKNOWN` → `OFFERED`).
6. **간편 알리기와 상세 접수를 나눈다(ADR-019 확장, ADR-026 결정 3 변경).** 공개 결함과 맞는 상담을 마치면 주 버튼 [확인한 내용으로 접수하기](상세 접수, 확인 화면에서 고친 뒤 제출, 같은 결함인지는 담당자가 판단)와 보조 버튼 **[같은 오류로 간편 알리기]**를 둔다. 간편 알리기는 대화 안 확인 카드에서 "「결함 제목」과 같은 오류예요"를 FC가 직접 누를 때만 기존 같은 오류 참여(`ME_TOO`)를 만들고, 상담에서 확인한 허용 코드(발생 기기·발생 조건·업무 영향·임시조치 상태·업무 재개·추가 지원 필요)만 붙인다. 이 참여는 지금처럼 FC가 공개 결함을 직접 고른 것이므로 담당자의 신고 연결(REQ-LG-02)과 다르다. 같은 사용자가 같은 결함에 이미 참여했거나 그 결함에 연결된 접수가 있으면 **새 기록을 만들지 않고** 그 접수를 돌려준다. 같은 요청 식별자로 다시 보내도 같은 접수다. 참여 뒤 내 접수내역·알림 받는 사람·관리자 화면은 기존 참여와 같다.
7. **상담 사례 재검증.** 확인 화면에서 업무·대표 증상·`guide` 조건을 바꾸면 상담이 안내한 사례를 다시 본다. 업무가 다르거나, 증상이 둘 다 있으면서 다르거나, 그 결함의 핵심 조건과 다른 값(모름 제외)을 고르면 `suggestedDefectId`·시도한 조치·`workaroundState`·`workOutcome`·그 결함의 조건 값을 지우고 "업무나 증상이 바뀌어 AI 문의에서 안내한 사례를 뺐어요"를 보인다. 저장할 때(`storedReport`)와 규칙 후보 계산(`ruleCandidates`)도 업무가 다른 안내 사례는 버린다. 점수·비슷함 정도는 계속 만들지 않는다.
8. **결함 대장 신고 패널을 세 덩어리로 나눈다.** ① **FC가 확인한 정보**: 발생 환경·재현 조건·업무 중단 여부·임시조치 상태와 결과(값마다 출처). ② **기존 결함과의 연관성**: 규칙·AI 후보마다 추천 근거, 연결된 신고 수, 영향 지점 수, 기존 조치(지금 상태·임시 방법·마지막 상태 변경). 두 수는 가상 데이터에서 센다. ③ **담당자 처리**: 같은 결함인지 확인 후 묶기, **추가 확인이 필요한 조건**(모름·빈 값), "수정 계획은 기술 검토 뒤 담당자가 [상태 바꾸기]에서 등록해요. 신고가 늘어도 예정일은 정해지지 않아요." 대표 결함 상세에는 묶인 신고의 발생 조건을 값별로 센 **"현장 조건 모아 보기"**를 더한다. 수정 예정 대화상자에는 시연 날짜가 가상이라는 안내를 둔다. 임시 방법이 없는 결함의 "수정 예정" 알림 문구는 "안내된 임시 방법을 써 주세요" 대신 "임시 방법은 아직 없어요"로 채운다.
9. **관리자 [지점 FC 문의]를 FC 단위로 묶는다(ADR-025 결정 6 변경).** 대표 결함마다 FC 한 줄("조은별(가상) FC · 관련 신고 2건 · 최근 업무 상황: 업무 진행 어려움")로 보이고, 줄을 펼치면 신고 건별(접수번호·날짜·접수 방식·알림 확인·업무 상황)을 본다. 업무 상황은 **업무 재개**(회신 `RESUMED`) · **업무 진행 어려움**(회신 `STILL` 또는 `supportNeeded=YES`) · **회신 없음**(임시 방법이 있는데 답이 없거나 "확인할 수 없어요") · **임시조치 미확인**(연결 전이거나 임시 방법이 아직 없음) 네 가지이고, FC의 가장 최근 기록으로 정한다. 회신 없음을 업무 중단으로 세지 않는다. 탭 위에 "지금 업무를 못 하는 FC / 추가 확인이 필요한 FC(회신 없음·임시조치 미확인) / 업무를 재개한 FC" 요약을 둔다. 전화·메신저 연결 버튼은 만들지 않는다. 보이는 범위는 지금과 같다(같은 지점 FC + 내가 대신 접수한 건, FC가 적은 설명은 내가 대신 접수한 건만).
10. **업무 재개 기록을 한 번만 남긴다.** `postWorkResumption`은 같은 신고·같은 신고자·같은 결과를 다시 받거나 같은 요청 식별자를 다시 받으면 새 기록·후속 기록을 만들지 않고 기존 기록을 돌려준다(`duplicate:true`). 접수 완료 처리는 업무 재개 기록을 **한 번만** 시도한다. 실패해도 접수번호는 그대로 보이고, 완료 화면에 "업무 재개는 아직 기록하지 못했어요"와 [다시 기록하기]를 둔다. 접수 성공과 후속 기록 성공을 따로 표시한다.
11. **본인확인 입력 오류의 개인정보 규칙.** 화면·자료·저장소·로그·검사에는 입력란의 위치(앞자리/뒷자리)와 키패드 표시 여부만 쓴다. 주민등록번호·고객번호·휴대전화번호는 쓰지 않는다. 입력 차단은 지금 형식(숫자 6개 이상·이메일)에 더해 "주민·뒷자리·앞자리·생년월일" 뒤에 붙은 숫자를 막는다. 고객 휴대전화의 OS·접속 경로는 FC 진술(`USER_REPORTED`)로만 남긴다. 가상 키패드 오류 화면은 만들지 않는다. 브라우저 자동 검사는 화면 흐름만 확인하며, 실제 스마트폰 OS 키패드가 나타나는지는 검증하지 않는다(실제 기기 확인 필요).

## 대안(불채택)
- **D-2026-001을 새 시나리오로 덮어쓰기 / `SEMINAR_HISTORY`를 새 조건 이름으로 바꾸기:** 기존 시연과 회귀 검사가 깨지고, 서로 다른 결함의 조건이 한 키에 섞인다.
- **새 오류를 청약·서명(`SUBSCRIPTION`)에 넣기:** 담당·후보가 전자서명 결함과 섞여, 업무가 같다는 이유만으로 D-2026-001·002가 후보가 된다.
- **임시조치가 없을 때 `STILL`을 그대로 쓰기:** "시도했지만 안 됨"과 "시도할 방법이 없음"이 같은 값이 되어 관리자 집계와 IT 판단이 틀어진다.
- **간편 알리기를 AI가 자동으로 참여시키기:** FC의 확인 없이 신고가 생기고, AI 추천 ≠ 같은 결함 확정 원칙에 어긋난다.
- **신고가 늘면 수정 예정일을 자동으로 제안:** 검증하지 않은 일정이 FC에게 나간다.
