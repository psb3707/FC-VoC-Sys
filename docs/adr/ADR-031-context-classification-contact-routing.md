# ADR-031. 문의 맥락 분류·담당 그룹 연결·업무 지원 연락처

- 상태: 승인 (결정자: 사용자, 2026-11-28 대화에서 승인. 업무 체계는 기존 7종 유지 + 세부 업무 추가, 빠른 접수의 업무 선택은 선택 사항, FC에게 인수 뒤 담당자 이름·가상 내선 표시).
- 근거: "FC-VoC-Sys — 업무 자동 분류·담당자 매핑·접수 완료 화면 고도화" 지시서, 분석 [context-classify-analysis-2026-11](../proposals/context-classify-analysis-2026-11.md)
- 구현 순서: Phase 1(P0) = 결정 1~5, 결정 6의 기본 화면, 결정 9. Phase 2(P1) = 결정 6의 담당자 이름·연락처, 결정 7·8. Phase 3 = 검증(결정 10).
- 바꿈:
  - ADR-030 결정 3: 분류 근거 순서, 상위 업무 8개
  - ADR-030 결정 6: IT 협의 알림 수신자
  - ADR-030 결정 8: IT 조회 범위
  - ADR-019 결정 1: 빠른 접수의 업무 선택 필수
  - ADR-025 결정 2·ADR-030 결정 4: FC에게 보이는 담당자 표시
- 유지:
  - ADR-030의 문의함 전달 → 인수 → 대응 기록 → IT 협의 → ITGS 초안(복사만)
  - 공통 오류 상태·연결은 사람(ADR-017), 자유 입력 원문은 페이지 메모리(ADR-021), 신원 검증(ADR-028), 현장 확인(ADR-029)
  - 기존 업무 코드 7종, 내부 필드·주소 키, S5 실험 경로(09번)

## 배경
지금 분류는 FC가 고른 업무에 거의 의존한다. 빠른 접수는 업무 선택이 필수이고, AI 문의는 알려진 결함 7건과 맞을 때만 업무를 안다. IT 협의는 IT 역할 전원에게 간다. 접수 완료 화면은 문의함 이름만 보이고, FC는 급할 때 어디에 연락할지 모른다.

## 결정

### 1. 업무 분류 체계 (가상, 기존 코드 유지 + 추가)
- **상위 업무 9개:** 고객관리 · 상품소개동의 · 가입설계 · 선심사 · 청약 · 신계약심사 · 계약관리 · 공통업무 · 기타(업무 미확인). 기존 "심사"를 선심사·신계약심사로 나눈다.
- **세부 업무:** 기존 7종(`LOGIN`·`SUBSCRIPTION`·`CUSTOMER_LOOKUP`·`DESIGN`·`CONTRACT_LOOKUP`·`CUSTOMER_CONSENT`·`ETC`)은 그대로 둔다. `PRE_UW`(선심사)·`UW_NEW`(신계약심사)·`APPLICATION`(청약서 작성·제출)·`E_SIGN`(전자서명)을 더한다.
- **전자서명.** 전자서명은 여러 업무에 쓰이므로 "서명"이라는 낱말만으로 부서를 정하지 않는다. 오류가 난 단계(청약 서명인지 등)가 확인될 때 정한다.
- **한곳에서 관리.** 업무 표·업무 표현(동의어·대표 증상·오타 변형)·모호 규칙·담당 그룹은 `fixtures/business-routes.js` 한 파일에 둔다. 분류 함수는 이 표만 읽는다.

### 2. 문의 맥락 분류 (규칙, AI 아님)
- **근거(종합).**
  1. FC가 고른 업무
  2. FC 확인 응답(분류 질문의 답)
  3. 오류가 난 화면 ID(접수한 PC 화면이 아님, ADR-028)
  4. 문장 규칙: 대상 낱말과 동작·증상이 함께 맞을 때만 근거로 친다. 낱말 하나만 맞으면 후보로만 둔다.
  5. 기존 유사 오류 이력
- **확정.** 근거가 한 세부 업무를 가리키면 확정한다. 근거끼리 다른 상위 업무를 가리키거나(예: 고른 업무와 화면이 다름), 모호 규칙에 걸리면 확정하지 않는다.
- **질문.** 확정하지 못하면 질문 하나를 선택지와 "잘 모르겠어요"로 묻는다. 이미 말한 것은 묻지 않는다. 답하지 않아도 접수할 수 있다.
- **못 정하면.** 업무가 둘 이상이면 공통 분류 문의함, 근거가 없으면 미분류 문의함으로 보내고 담당자가 재분류한다.
- **저장.** 업무 코드·세부 업무·확정 여부·방식(`RULE`)·근거 코드·추가 확인 항목·재분류 이력을 저장한다. 문장 원문은 저장하지 않는다(ADR-021). 확률·정확도 숫자는 만들지 않는다.
- **교체 지점.** 문장 규칙은 `classifyText` 하나로 두어 나중에 LLM 분류로 바꿀 수 있게 한다. 지금은 LLM이 없고, 화면에 "규칙으로 분류"라고 쓴다.
- **역할별 표시.** FC에게는 "○○ 업무 관련 문의로 확인했어요"와 [업무 바꾸기]만 보인다. 담당자에게는 업무 코드·근거·미확인 항목을 보인다.

### 3. 업무분장과 담당자 (가상)
- **세 가지를 나눈다.**
  - 담당 그룹: 그 업무 문의를 받는 부서 문의함
  - 업무 연락처: 그 그룹의 대표 업무 지원 연락처(가상 내선)
  - 실제 처리 담당자: 그 문의를 인수한 사람
- **업무 매핑.** 세부 업무 → 현업 담당 그룹·IT 담당 그룹·사용 여부. 담당 그룹에는 업무 연락처·대체 그룹·사용 여부를 둔다.
- **담당자.** 사용자에 맡은 그룹(현업 `inboxIds`, IT `itGroupIds`)·업무 연락처(가상 내선)·주/대체 담당·사용 여부·인수 가능 여부를 둔다. 한 사람이 여러 그룹, 한 그룹에 여러 사람이 가능하다.
- **하드코딩 금지.** 이름을 업무 코드에 넣지 않는다. 담당자가 바뀌어도 기존 문의·대응 기록은 그때의 사용자 ID를 그대로 가리킨다.
- **AI 한계.** 담당자 이름·연락처·부서는 표에서만 읽는다. 분류 규칙·AI가 만들지 않는다.

### 4. 현업 담당 그룹 연결
- **기본은 문의함 전달 + 인수.** 개인 자동 배정은 하지 않는다. 접수만으로 담당자가 정해졌다고 쓰지 않는다.
- **부재·비활성.** 담당 그룹에 사용 중이고 인수할 수 있는 구성원이 없으면 대체 그룹으로 보낸다. 대체도 없으면 공통 분류 문의함으로 보낸다. 근거는 경로에 남긴다.
- **매핑 누락.** 세부 업무에 담당 그룹이 없거나 사용 중이 아니면 공통 분류 문의함으로 보낸다.
- **재분류.** ADR-030 그대로(같은 문의, 이력 덧붙이기). 최초 업무·바뀐 업무·사유·담당자·시각을 남긴다.

### 5. IT 담당 그룹
- **그룹.** IT 협의 영역(`itArea`)마다 IT 담당 그룹(가상)을 둔다. 그룹이 없거나 사용 중인 구성원이 없으면 공통 IT 협의함으로 보낸다.
- **알림·조회.** IT 협의 요청은 그 그룹 구성원에게만 알리고, IT는 내 그룹 협의 요청과 공통 오류를 본다.
- **IT 인수.** IT 담당자는 [협의 맡기]로 협의를 인수한다. 현업 인수와 따로 기록하고 한 협의에 한 명이다. IT 협의를 요청해도 현업 담당자는 그대로다.
- **영역 변경.** 현업 담당자는 IT 협의 요청 때 IT 담당 그룹을 바꿀 수 있다.
- **같은 문의.** 협의는 원본 문의를 가리키는 기록이다. 문의를 새로 만들지 않는다. 공식 요청은 ITGS(ADR-030 결정 5).

### 6. 접수 완료 화면과 담당자 표시
- **접수 완료.** "문의가 접수되었어요" + "○○ 업무 담당 부서에 전달했어요". 문의 정보(문의번호·관련 업무·세부 업무·담당 부서·처리 상태), 업무 지원 연락처(가상), 버튼 [문의번호 복사]·[내 문의 및 처리 경과]·[업무 지원 연락처]·[닫기].
- **상태별 담당자 표시.**

  | 상태 | FC에게 보이는 것 |
  |---|---|
  | 접수 완료·인수 전 | 담당 부서·업무 연락처, "담당자 확인 대기 중" |
  | 인수 뒤 | 실제 담당자 이름(가상)·업무 연락처(가상 내선) |
  | 담당 변경·재분류 | 바뀐 부서·담당자 |
  | IT 협의 중 | 현업 담당자와 "IT와 확인 중". 현업 지원 경로 유지 |
  | 처리 완료 | 처리 결과와 추가 지원 경로 |
  | 업무 미확인 | 공통 문의함과 그 연락처 |

- **IT 연락처.** FC에게 보이지 않는다. 현업 담당자 화면에서만 IT 담당 그룹·협의 담당자·업무 연락처를 보인다. 협의를 요청하지 않았으면 IT가 처리 중이라고 쓰지 않는다.

### 7. 연락처 원칙
- 가상 업무용 내선만 보인다. 개인 휴대전화는 없다.
- 연락처가 없으면 만들지 않고 "등록된 연락처 없음"으로 쓴다.
- 비활성 담당자는 새 전달 대상이 아니고, 대체 연락처가 있으면 그것을 보인다.

### 8. 전화 문의 연계 (P1)
- **번호 조회.** 현업 담당자가 문의번호를 정확히 넣으면 내 범위의 문의는 상세를 연다. 범위 밖이면 "○○ 문의함에 있는 문의예요"만 보이고 상세는 보이지 않는다.
- **전화 대응 기록.** 대응 기록에 `PHONE`(전화로 확인함 + 확인한 조건 코드)을 더한다. 통화 내용 원문은 저장하지 않는다.
- **전화 먼저.** 관리자 대리 접수에 "전화로 먼저 문의함" 코드를 둔다. 같은 FC의 진행 중 문의가 있으면 새로 만들지 않고 그 문의에 덧붙이도록 먼저 보인다.
- **범위 밖.** CTI·통화 녹음·음성 분석·자동 발신·문자 발송

### 9. 권한
- FC 본인, 관리자 같은 지점, 현업 내 문의함·내가 인수한 문의, IT 내 그룹 협의 요청·공통 오류(ADR-030 결정 8 변경).
- 데이터 계층(`api-client.js`)에서 검사한다. 주소·번호 찾기로 열어도 범위 밖 상세는 보이지 않는다.
- 이 시제품의 검사는 브라우저 안의 검사다. 운영에서는 서버 인증·인가·감사 로그가 필요하다. 동시 인수 방지도 서버 트랜잭션이 아니다.

### 10. 검증
- **골든셋.** 가상 문의 30건 이상(업무명 명확·생략·동의어·구어체·오타·복수 업무·질문 필요·분류 불가·접수 화면과 실제 업무 다름·매핑 누락·담당자 부재). 정답은 `docs/golden/`에 따로 두고 "검토 전 예시"로 표시한다.
- **E2E.** E01~E26(지시서 10.2절)을 `scripts/`의 검사로 실행한다.
- **해석.** 규칙 검사 통과를 LLM 자연어 이해 성능으로 보고하지 않는다. 모호한 문의를 질문으로 넘긴 것도 맞은 처리로 센다.

## 대안(불채택)
- **업무 코드 전체 교체(`CUSTOMER`·`APPLICATION` 등으로):** 저장된 시연 상태·회귀 검사·S5 경로가 바뀐다. 추가만 한다.
- **개인 자동 배정:** 실제 업무분장 정책이 확인되지 않았다.
- **분류 확률 표시:** 검증되지 않은 숫자를 만들게 된다.
- **LLM 분류 연결:** 실제 LLM이 연결·검증되지 않았다. 교체 지점만 둔다.
