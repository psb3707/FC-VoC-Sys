# ADR-026. AI 문의의 되묻기·임시 방법 결과를 접수와 결함 대장까지 잇는다 (전자서명 오류 E2E)

- 상태: 승인 (결정자: 사용자, 2026-11-15 "전자서명 오류 E2E 시연 완성을 위한 P0 개발 지시서")
- 확장: ADR-018(AI 문의: 한 번 묻고 답하기 → 한 상담 안에서 최대 3개 되묻기와 임시 방법 결과 확인), ADR-019·021·022(공유 저장소에 둘 수 있는 구조화 값에 발생 조건·출처·상담 결과 코드 추가), ADR-017(프론트 단계에서 고정 응답이 없는 새 신고의 후보 계산), ADR-025(업무 재개 회신을 접수 직후 신고자 본인 회신으로 기록)
- 유지: 사람이 대표 결함에 연결한다(REQ-LG-02, ADR-017). 임시조치 성공 ≠ 해결, AI 추천 ≠ 같은 결함 확정, 접수 ≠ 담당자 확인(ADR-025 결정 7). 자유 입력 원문은 페이지 메모리에만(ADR-021). LLM에는 `MaskedInput`만(08번).

## 배경
- 시연 흐름 "FC 문의 → AI → 접수 → IT 연결 → 상태 변경 → FC·관리자 확인"이 각 화면에서는 동작하지만 한 사건으로 이어지지 않는다.
  1. AI 문의는 한 번 답하고 끝난다. 발생 기기·초대장 발송 이력처럼 같은 결함인지 가늠할 조건을 묻지 않고, 안내한 임시 방법이 통했는지도 묻지 않는다.
  2. [이 내용으로 문의 접수]는 질문과 업무·증상만 넘긴다. 대화에서 알게 된 사실은 접수에서 다시 고르거나 잃는다.
  3. 접수 확인 화면의 "세미나 초대장 발송" 답(evidence)은 공유 저장소에 남지 않아 결함 대장에서 보이지 않는다.
  4. 비슷한 대표 결함 추천은 신고 ID별 고정 응답이라 시연 중 새로 만든 신고(`R-Q…`)에는 "찾지 못했어요"만 나온다.

## 결정
1. **한 상담 안에서 되묻는다(S2 AI 문의).** 공개 결함과 맞는 질문이면 그 결함에 정해 둔 확인 항목(시연: 발생 기기·초대장 발송 이력·고객 대기 여부)을 **최대 3개** 묻는다. 질문 문장에서 이미 알 수 있는 항목과 이 상담에서 답한 항목은 다시 묻지 않는다. 모든 항목에 "잘 모르겠어요"가 있어 건너뛸 수 있다. 묻고 답한 내용은 대화 줄로 쌓인다(새 질문을 보내도 앞의 대화는 남는다). 확인 항목과 문장은 시연 시나리오 자료(`fixtures/intake-assistant.js`)에 두고, 결함 상태·임시 방법·예정일은 계속 결함 대장에서 읽는다(문자열을 새로 복사하지 않는다).
2. **임시 방법 결과를 묻는다.** 결과 카드(ADR-025 두 갈래 표시) 뒤에 "이 방법으로 업무를 이어갈 수 있었나요?"(시나리오에 정한 문장이 있으면 그 문장)를 묻고 **진행했어요(`RESUMED`) / 아직 안 돼요(`STILL`) / 지금은 확인할 수 없어요(`UNKNOWN`)** 중 고른다. 답은 접수 전까지 **상담 결과(페이지 메모리)**일 뿐이고 대표 결함 상태를 바꾸지 않는다. 접수번호가 생기기 전에는 `postWorkResumption`을 부르지 않는다.
3. **주 버튼은 하나.** 되묻기·결과 확인을 마친 상담은 아래 행동 줄의 주 버튼 **[확인한 내용으로 접수하기]** 하나로 접수 확인 화면(`step=review`)에 간다. 이때는 [AI와 접수 초안 만들기] 알약을 숨긴다(같은 일을 두 번 하지 않음). 되묻기가 없는 답(사용법·찾지 못함·조회 실패)은 지금처럼 [이 내용으로 문의 접수]와 [AI와 접수 초안 만들기]를 둔다. AI 조회가 실패해도 쓴 질문을 그대로 일반 접수로 옮긴다.
4. **인계(handoff).** 상담 결과를 구조화 객체로 넘겨 확인 화면을 미리 채운다: 업무·대표 증상, 발생 기기(`CUSTOMER_PHONE` 새 코드 "고객 휴대전화"), 발생 조건(`conditions.SEMINAR_HISTORY` = `YES|NO|UNKNOWN`), 업무 영향(고객 대기 → 긴급 사정 `CONSULTING`), 시도한 조치(안내한 결함의 임시 방법, 대장 문장 그대로), 조치 결과(`workOutcome`), AI가 안내한 사례(`suggestedDefectId`, 후보일 뿐 연결 아님). 확인 화면의 카드 **"AI 문의에서 확인한 내용"**에서 각 값을 고칠 수 있고, 고친 값으로 제출한다. 이미 답한 값은 다시 고르게 하지 않는다.
5. **공유 저장소에는 허용된 코드만 둔다.** 접수 저장본(`storedReport`)에 `origin`(`ASSISTANT|FORM`), `conditions`, `workOutcome`, `suggestedDefectId`, `factSources`를 더한다. 값은 허용 목록에 있는 코드만 남기고 나머지는 버린다. 대화 원문·고객 이름·연락처·계약번호·기기 토큰은 저장하지 않는다. 접수번호는 지금처럼 `R-Q…`, 같은 `requestId`로 다시 보내면 같은 접수를 돌려준다.
6. **출처를 구분한다.** `factSources`의 값은 `USER_REPORTED`(FC가 알려 줌) · `DEMO_CONTEXT`(접수 화면 자동 기록, 시연 진단값) · `BROWSER_CAPTURED`(실제 브라우저 확인, 백엔드 단계) · `DEFECT_LEDGER`(결함 대장의 값) · `UNKNOWN`(미확인)이다. 고객 휴대전화의 기기·로그는 FC 진술(`USER_REPORTED`)로만 남기고 자동 수집처럼 표시하지 않는다.
7. **업무 재개 회신은 접수 직후 본인만 기록한다.** 상담에서 `RESUMED|STILL`을 고른 FC가 **자기 이름으로** 접수하면, 접수번호가 생긴 뒤 기존 `postWorkResumption(reportId, 신고자, 결과)`로 기록한다(ADR-025 결정 5의 신고자 본인 규칙, `STILL`은 후속 기록도 남김). 대리 접수에서는 관리자가 FC 대신 회신하지 않는다: `workOutcome`을 저장하지 않고 확인 화면에 "업무 재개 여부는 FC 본인이 내 접수내역에서 답해요"를 보인다. `UNKNOWN`은 회신 없이 접수 저장본에만 남는다.
8. **새 신고 후보는 규칙으로 계산하고 그렇게 표시한다(프론트 단계).** 고정 AI 응답이 없는 신고는 업무·대표 증상·발생 조건·시도한 조치·AI 문의가 안내한 사례를 대표 결함(시나리오의 업무·증상·조건, 묶인 신고의 업무·증상)과 비교해 후보를 최대 3개 돌려준다(`llmOutcome=RULE`). 업무와 증상이 모두 같거나 AI 문의가 안내한 사례일 때만 후보가 된다. 후보마다 **추천 근거**(업무·증상·관련 조건·시도한 조치·AI 문의에서 안내함)를 글로 보이고 비슷함 정도·점수는 붙이지 않는다(검증하지 않은 수치를 만들지 않음). 화면은 "규칙 후보 · 담당자가 확인해요"로 표시하고 연결은 담당자가 `postLinkReport`로만 한다. 고정 응답이 있는 신고, `llm=fail` 규칙 대체, 후보 없음, 최대 3개, 없는 결함 ID·중복 제거는 그대로다. 백엔드 단계에서는 ADR-017대로 AI가 후보를 내고 이 규칙은 실패 대체로 쓴다.
9. **결함 대장이 같은 저장본을 읽는다.** 신고 패널과 대표 결함 상세의 묶인 신고에 **"FC가 알려 준 발생 조건"**(발생 기기·초대장 발송 이력·업무 영향·시도한 조치·업무 재개·AI 문의 안내 사례, 값마다 출처)을 보인다. S2 완료 → S4 → S3 → 역할 전환 → 새로고침에서 같은 신고번호가 같은 값을 보인다.

## 대안(불채택)
- **새 상담 API(`POST /api/intake/consultations`)를 따로 만든다:** 프론트 단계에서는 상담 상태가 페이지 메모리에만 있어 API가 늘 뿐 얻는 것이 없다. 백엔드 단계에서 상담 기록 보관이 필요해지면 다시 본다.
- **상담 중 답을 바로 `postWorkResumption`에 기록:** 접수번호가 없어 기록할 곳이 없고, 접수하지 않은 상담이 결함 대장 집계에 섞인다.
- **새 신고에 HIGH/MEDIUM 비슷함을 붙인다:** 규칙 계산에 근거 없는 정도를 붙이게 된다.
- **접수 초안(ADR-022)에 대화 내용을 글로 채운다:** 같은 사실이 구조화 값과 초안 글에 두 번 생기고, 저장소에는 초안 글이 남지 않아 대장에서 볼 수 없다.
