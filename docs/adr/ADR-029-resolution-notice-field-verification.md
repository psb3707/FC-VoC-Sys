# ADR-029. 알림 요약, 수정·배포 검증 완료, FC 현장 정상 이용 확인

- 상태: 승인 (결정자: 사용자, 2026-11-22 대화에서 승인. "알림 UX 개선 및 결함 해결 완료 후 현장 확인 기능 개발" 지시서)
- 바꿈:
  - ADR-025 결정 1: 질문형 제목 → "지금 가능한 대응" / "오류 수정 진행상황". 두 관점은 유지
  - ADR-025 결정 8: 알림 팝업은 요약, 내 접수 카드는 상태 → 대응 → 경과 → 상세 이력 순서
  - ADR-021 해결 안내: "수정 완료" 표현은 검증 기록이 있을 때만
  - ADR-027 결정 9: 해결된 결함의 관리자 집계를 현장 확인으로, 해결 전 FC 대표 상황 규칙을 정정
- 유지: 상태 7종, 알리는 변경 4가지, 수신자·사람별 1건(ADR-025 결정 4), 업무 재개 회신(ADR-025 결정 5), 사람이 연결(ADR-017), 자유 입력 원문은 페이지 메모리에만(ADR-021), 신원 검증(ADR-028).
- 번호: ADR-023·024는 다른 브랜치가 쓰고 있다. 029는 2026-11-22 현재 모든 로컬·원격 브랜치에서 비어 있다.

## 배경 (6e8b9ed에서 실제로 재현)
1. 알림은 문장 하나다. 수정 예정 알림이 320px 팝업에서 다섯 줄이고 상태·할 일이 구분되지 않는다.
2. 검증 정보 없이 `RESOLVED`로 바꿔도 알림에 "수정 완료"라고 나간다.
3. 해결 뒤 FC가 실제로 되는지 답할 곳이 없고, 관리자 요약에서도 빠진다.
4. 접수 → 수정 예정으로 건너뛰면 문제 확인·원인 파악·임시조치까지 지나온 것으로 칠해진다.
5. "업무 진행 어려움"으로 신고한 FC가 업무 상황 없이 같은 결함을 다시 신고하면 "업무를 못 함"에서 빠진다. ADR-027의 "가장 최근 기록" 규칙과 E2E-04가 이 잘못된 결과를 정답으로 두고 있다.
6. 되돌림 사유는 화면에서 필수로 받지만 저장되지 않는다(02번 3절 위반). 재배포·재검토 이력을 구분하려면 필요하다.

## 결정

### 1. 상태와 검증 근거
- 새 상태 코드는 없다. `RESOLVED`는 "해결"이다.
- 해결 이력(`DefectStatusHistory`)에 선택 객체 `verification`을 둔다.
  `{result: VERIFIED, verifiedAt, usageGuide, workaroundEnded, refId?, environment?, version?, simulated: true}`
- `verification`이 있는 해결만 "수정 완료", "수정·배포 검증 완료"로 쓴다. 없으면 "해결"로만 쓰고, 기존 해결을 배포 완료로 읽지 않는다.
- 해결 화면 필수: 검증 여부(검증 완료 / 검증 근거 없음), 적용 시각, 적용 범위, 바뀐 동작, 기존 건 처리, 공개 확인. 검증 완료면 검증 완료 시각(적용 시각 이후)과 공개 정상 이용 안내도 필수다.
- 선택: 배포 참조 ID, 검증 환경, 배포 버전(형식 제한). 내부 조치 메모는 자유 입력이므로 페이지 메모리에만 두고 그렇게 표시한다.
- 프론트 단계의 검증 기록은 모두 `simulated: true`이고 "가상 · 시연용"으로 표시한다. 근본 원인·코드 수정 내용은 만들지 않는다.
- 임시 방법이 있던 결함은 담당자가 "사용 종료 확인"을 고른 경우에만 종료를 안내한다. 아니면 "종료 여부 확인 전"이다.

### 2. 현장 확인 `FieldVerification` (업무 재개와 별도)
- `{id, reportId, defectId, resolutionEventId, result, at, actorId, requestId}`. 덧붙이기만 한다.
- `result`: `CONFIRMED_OK` 정상 진행했어요 / `STILL_FAIL` 아직 문제가 있어요 / `NOT_TESTED` 아직 확인하지 못했어요.
- 받는 조건: 신고자 본인, 그 결함에 연결된 신고, 결함이 지금 `RESOLVED`이고 `verification`이 있으며 `resolutionEventId`가 지금 해결 이력일 때. 관리자·영업·IT는 대신 답하지 못한다.
- 멱등: 같은 요청 ID이거나 같은 신고·해결 이력의 마지막 결과와 같으면 기존 기록을 돌려준다. 다시 답해 결과가 바뀌면 새 기록이다.
- `STILL_FAIL`만 후속 기록 `FIELD_FAIL`을 남기고 추가 상황 입력(기존 후속 입력)으로 안내한다. `NOT_TESTED`는 미확인이며 후속 기록·긴급 표시가 없다.
- 어떤 답도 결함 상태·알림을 바꾸지 않는다. FC 전원 회신은 해결의 조건이 아니다.
- 해결 이력이 바뀌면 새 이력의 확인은 모두 미확인에서 시작한다. 이전 답은 상세 이력에만 남는다.

### 3. 알림 요약
- `NotificationLog.summary {title, status, headline, line, action}`를 보낼 때의 값으로 남긴다. `bodySnapshot`은 유지한다.
- 팝업: 오류명(2줄 이내), 상태 태그 하나, 핵심 안내, 보조 안내(각 2줄 이내), 시각, 행동 글 하나. 줄 전체가 버튼 하나다.
- 오류명은 대표 결함의 짧은 공개 이름 `shortTitle`(예: "고객 동의 입력 오류"), 없으면 제목을 2줄로 줄인다.
- 날짜는 수정 예정에만 쓴다. 지난 알림은 보낸 때의 상태를 유지한다.
- 누르면 같은 접수번호의 카드로 간다. 읽음은 현장 확인이 아니다.

### 4. 내 접수 카드
- A 현재 상태: 담당자 확인 전 / 확인 중 / 임시 방법 안내 / 수정 예정 / 수정 완료(검증 있음) / 해결(검증 없음) / 수정하지 않음
- B 지금 가능한 대응: 임시 방법, 없음, 또는 정상 이용 안내 + 현장 확인 질문
- C 오류 수정 진행상황: **실제 기록이 있는 단계만** 시각과 함께. 대장 상세도 같은 규칙
- D 상세 이력(접힘): 상태 이력, 공개 안내, 일정 변경, 후속·확인 기록
- 같은 문장을 B·C·D에서 되풀이하지 않는다.

### 5. IT 결함 상세
- "수정 완료 후 현장 확인": 정상 확인·문제 지속·미확인 FC 수와 신고 수를 계산한다.
- 문제 지속 FC와 그 신고의 발생 조건, 후속 조사 기록(코드: 조사 시작 / 추가 정보 필요 / 재현 안 됨 / 잔존 가능성)을 둔다.
- 재검토는 기존 [상태 바꾸기]로만 한다. 자동 재오픈·원인 확정은 없다.

### 6. 관리자 [지점 FC 문의]
- 검증 완료된 결함: 문제 지속 → 추가 지원 필요, 정상 확인 → 정상 진행 확인, 미확인 → 확인 필요.
- FC 대표 결과는 그 해결 이력에서 **가장 최근에 실제로 남긴 답**이다. 답 없는 다른 신고가 덮지 않는다. 신고별 답은 펼쳐서 본다.
- FC 수와 신고 수를 따로 쓴다(FC 3명 · 신고 4건).
- 해결 전 대표 상황(사용자 선택): **FC가 명시한 가장 최근 상황.** 업무 재개 회신과 `supportNeeded=YES|NO`가 명시한 상황이다. 상황을 적지 않았거나 `UNKNOWN`인 신고는 앞선 상황을 덮지 않는다.

### 7. 재배포와 되돌림
- 재배포(사용자 선택): **되돌린 뒤 다시 해결.** 앞 단계로 되돌리고(알림 없음) 다시 해결하면 새 해결 이력·알림 1건·새 현장 확인이 된다. 수정 예정으로 되돌릴 때도 예정일은 필수다.
- 되돌림 사유는 코드(현장 문제 재검토 / 재배포 준비 / 잘못 기록 / 기타)로 저장한다. 설명은 페이지 메모리에만 둔다.

### 8. 알림 정책 (새 알림 이벤트 없음)
- 알림: 임시조치, 수정 예정, 해결(검증 완료면 확인 유도), 수정하지 않음, 기존 대리 접수.
- 기록만: 배정, 원인 분석, 되돌림, FC 현장 확인, 후속 조사.
- 예정일 변경 알림은 ADR-025 보류를 유지한다.

### 9. 권한·개인정보
- 알림·현장 확인·조사 기록에는 코드와 승인된 공개 안내만 둔다. 고객 식별정보·고객 URL·토큰·자유 입력 원문은 없다.
- 관리자는 지점 범위의 요약만 보고, 계정 ID·FC 설명은 기존 규칙을 따른다.
- 백엔드 단계에서는 `actorId`를 인증 세션에서 정하고 서버가 권한을 다시 검증한다.

### 10. 같은 화면에서 함께 바로잡는 #26의 정확성 문제 (사용자 선택: 이 브랜치에서 처리)
- 관리자 FC 누락(결정 6), 건너뛴 단계 표시(결정 4).
- 규칙 후보를 "AI 추천"이라고 쓴 안내 문구, 로그인 사용자와 다른 홈 머리글 지점.
- 같은 오류 참여(`ME_TOO`)는 담당자의 연결이 아니므로 "담당자가 확인했어요"로 쓰지 않는다(ADR-027 결정 6과 일치).
- 알림을 받는 시드 신고자도 자기 접수 카드를 열 수 있어야 한다(내 접수내역은 본인의 모든 신고를 읽는다).

## 대안(불채택)
- 업무 재개 회신에 현장 확인을 저장: 임시 방법으로 진행한 것과 수정된 것이 섞인다.
- 새 상태 `DEPLOYED`·`FIELD_CONFIRMED`: FC 답이 결함 상태를 좌우하고 7단계 명세가 깨진다.
- 문제 지속 회신 때 자동 재오픈: 재발 판단은 IT 담당자의 일이다.
- 팝업 문장만 줄이기: 상태·할 일을 구조로 나눌 수 없고 지난 알림의 상태를 보존하지 못한다.
