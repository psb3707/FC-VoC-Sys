# ADR-030. 업무 분류·담당 문의함·현업 초기 대응·IT 사전 협의

- 상태: 승인 (결정자: 사용자, 2026-11-25 대화에서 승인. 범위 P0 먼저, 현업 담당자는 `SALES` 역할 재사용, 업무 코드는 기존 7종 + 상위 업무).
- 구현 순서: P0 = 결정 2~5, 결정 6의 신규 문의·IT 협의·추가 정보 필요·대응 안내 알림, 결정 8. P1 = 결정 6의 문제 지속 알림·외부 채널 미리보기, 결정 7. P1은 P0 검증 뒤 다시 정한다. 근거: "실제 업무 프로세스 기반 PoC 고도화 개발 지시서", 분석 [ops-workflow-analysis-2026-11](../proposals/ops-workflow-analysis-2026-11.md)
- 바꿈:
  - ADR-025 결정 2: 연결이 곧 담당자 확인 → 인수 또는 연결
  - ADR-025 보류 중 새 알림 이벤트 일부(결정 6)
  - ADR-017 결정 5: 새 신고 알림 수신자 → 담당 문의함
  - 02번 4절: 알림은 결함 상태 변경만 → 문의 단위 알림 추가
  - ADR-029 결정 2: 현장 확인 문구
  - 06번·ADR-015의 화면 용어
- 유지:
  - 공통 오류 상태 7종과 전이·검증·되돌림(02번 3절, ADR-029), 연결은 사람(ADR-017)
  - 자유 입력 원문은 페이지 메모리(ADR-021), 신원 검증(ADR-028), 현장 확인은 신고자 본인 FC(ADR-029)
  - S5 실험 경로(09번), 내부 코드·필드·주소 키, 부지점장·지점장 미구분(ADR-025 보류)

## 배경
IT 담당자 인터뷰에서 확인한 업무 순서는 다음과 같다(지시서 1절).
- 오류 문의는 먼저 관련 현업부서가 받는다. 현업은 자체 해결하거나, IT와 전화로 협의한다.
- 코드 수정이 필요하면 현업이 그룹웨어 ITGS에 공식 요청을 올린다. 합의·결재·배정·개발은 ITGS에서 하고, ITGS 상태는 진행중·반려종료·정상종료다.

지금 시연은 IT가 신고번호를 이미 알고 검색하며 시작한다. 업무에 맞는 담당자에게 문의가 가지 않고, 결함으로 확인되기 전에는 문의에 대응할 방법이 없다.

## 결정

### 1. 시스템의 자리
FC-VoC-Sys는 ITGS를 대체하지 않는다. 문의 접수, 업무 분류와 전달, 현업 초기 대응, IT 사전 협의, 결과 안내, 대응 지식 재사용을 돕는다. 공식 요청·합의·결재·배정·배포는 기존 절차를 따르고 여기서 만들지 않는다.

### 2. 용어 (화면 문구만, 내부 이름 유지)
| 기존 | 새 이름 |
|---|---|
| 결함 대장 | 전산 문의 관리 |
| 아직 안 묶인 신고 | 신규 문의(문의함) |
| 대표 결함 | 공통 오류 |
| 신고 | 문의 |
| 신고번호 | 문의번호 |
| 신고자 | 문의자 |
| 결함 상세 | 오류 상세 |
| 상태 이력 | 오류·조치 이력 |
| 신고 묶기 | 관련 오류 연결 |
| 비슷한 결함 | 유사 오류 사례 |

- 문맥에 맞게 고르고, 한꺼번에 바꾸지 않는다.
- FC 화면은 "전산 문의하기"와 "내 문의 및 처리경과"로 부른다.

### 3. 업무 분류와 전달 (규칙, AI 아님)
- **업무분장 표(가상).** 기존 업무 코드 7종을 세부 업무로 두고 상위 업무 8개에 연결한다.
  - 상위 업무: 고객관리 · 상품소개동의 · 가입설계 · 청약 · 심사 · 계약관리 · 공통업무 · 기타
  - 항목마다 관련 화면 ID, 문의함, IT 협의 영역, 사용 여부를 둔다.
  - 부서·문의함은 모두 가상이며 실제 업무분장이 아니다.
- **분류 규칙(순서대로).**
  1. FC가 고르거나 확인한 업무
  2. 오류가 난 화면 ID(접수한 PC 화면이 아님, ADR-028)
  3. 증상과 기존 이력
  - 근거를 함께 저장하고 화면에 "규칙으로 분류"라고 쓴다.
- **예외.**
  - 업무가 하나면 그 부서 문의함으로 보낸다.
  - 둘 이상이면 공통 분류 문의함으로 보낸다.
  - 근거가 없으면 미분류 문의함으로 보낸다.
- **재분류.**
  - 담당자가 [다른 문의함으로]와 사유 코드로 바꾼다.
  - 문의·대화·이력은 그대로 두고 재분류 이력을 덧붙인다. 문의자는 다시 접수하지 않는다.
- **교체 가능.** 분류는 `classifyInquiry` 한 곳에 두어 나중에 LLM 분류로 바꿀 수 있게 한다.
- **AI 한계.** AI는 담당자 이름·조직을 만들지 않는다.

### 4. 담당 문의함과 인수
- **현업 담당자.** 기존 `SALES` 역할을 현업 담당자로 쓰고, 맡은 문의함(`inboxIds`)을 둔다.
- **[전산 문의함].** 기본으로 내 문의함만 보인다. 요약은 신규·내 담당·추가 정보 확인 필요·IT 협의 필요다.
- **세 가지 확인.** 알림 읽음, 문의 확인(상세를 엶), 인수([담당하기])는 따로 기록한다. 대응 시작은 인수뿐이다.
- **중복 인수 방지.** 이미 다른 사람이 인수한 문의는 인수를 거부하고 담당자를 보여 준다. 담당 변경은 재분류로만 한다(재분류하면 담당이 비고 새 문의함에 신규로 들어간다).
- **FC 표시.** "담당자가 확인했어요"는 인수 또는 공통 오류 연결 뒤에만 쓴다(ADR-025 결정 2 변경). 알림 읽음·상세 열람으로는 바뀌지 않는다.

### 5. 문의 단위 대응 (결함 확인 전에도)
- **대응 기록.** 담당자는 덧붙이기 기록으로 대응한다. 문의 대응 상태는 마지막 기록에서 계산하며 새 상태 열을 만들지 않는다.

  | 기록 | 뜻 |
  |---|---|
  | 추가 정보 요청 | 필요한 항목 코드 |
  | 대응 방법 안내 | 승인·공개된 대응만 |
  | 자체 해결 | 적용한 대응 코드 |
  | IT 협의 요청 | IT에 확인할 질문 코드 + 현업이 확인한 내용·미확인 사항 |
  | IT 협의 결과 | 현장 안내 가능 / IT 확인 계속 / 수정·배포 필요(ITGS 요청 필요) / 재현 안 됨 |
  | 재분류 | 다른 문의함으로 보냄 |

- **추가 정보 요청.** 요청은 항목 코드(기기·OS, 링크를 연 경로, 문제가 생긴 단계, 반복 여부 등)로 보낸다. 문의자는 내 문의 카드에서 선택형으로 답하고("잘 모르겠어요" 포함), 답은 출처 "FC가 추가로 알려 줌"으로 문의에 붙는다.
- **자유 메모.** 메모는 그 화면에만 두고 저장하지 않는다(ADR-021).
- **대응 방법.** 기존 이력의 대응 방법은 담당자가 적용 여부를 판단해 고른다. AI·규칙이 만든 대응은 현장에 나가지 않는다.
- **공통 오류.** 연결은 지금처럼 담당자가 한다. 연결하지 않아도 문의는 끝날 수 있다(자체 해결).
- **ITGS 요청 초안.**
  - 확인된 정보로 요청 내용 요약(제목·배경·증상과 조건·업무 영향·현업 대응·IT 협의 내용·요청 조치)을 만들고 복사하게 한다.
  - 저장하지 않고, 실제 ITGS 양식처럼 꾸미지 않는다.
  - ITGS 결재·배정은 만들지 않는다.

### 6. 알림 (ADR-025 보류 일부 해제)

| 사건 | 받는 사람 | 종류 |
|---|---|---|
| 신규 문의 | 그 문의함 담당자 | `NEW_INQUIRY` |
| IT 협의 요청 | IT 담당자 | `IT_CONSULT` |
| 추가 정보 필요 | 문의자(대리 접수면 대리 접수자도) | `INFO_REQUEST` |
| 대응 방법 안내·자체 해결 | 문의자(대리 접수면 대리 접수자도) | `INQUIRY_GUIDE` |
| 문제 지속 응답 | 담당자와 IT | `FIELD_FAIL` |

- **기존 알림.** 공통 오류 상태 변경 알림(임시조치·수정 예정·해결·수정하지 않음)은 그대로다.
- **보내지 않는 것.** 관련 없는 문의함·부서에는 보내지 않는다. 예정일 변경 알림은 계속 보류한다.
- **중복 방지.** 키는 `eventId + recipientId + kind`이다. 이미 정상 이용을 확인한 FC에게는 확인 요청을 다시 보내지 않는다.
- **채널.**
  - 앱 내부 알림만 실제로 만든다.
  - 그룹웨어·메신저·Push·SMS·알림톡은 "발송 예시 · 연계 전" 미리보기로만 보이고 저장하지 않는다.
  - 발송 계층은 함수 하나로 나눠 둔다.

### 7. 현장 확인과 상태 분리
- **따로 두는 것.** 문의 대응 상태, ITGS 공식 요청 상태, 공통 오류의 수정·검증, FC 정상 이용을 섞지 않는다.
- **ITGS.** ITGS 정상종료를 검증 완료로 보지 않는다.
- **현장 확인 문구(코드는 그대로).** 정상적으로 이용했어요 / 아직 문제가 발생해요 / 아직 다시 이용하지 않았어요
- **자체 해결 문의.** 자체 해결된 문의도 문의자가 FC면 같은 방식으로 확인을 받는다.

### 8. 권한
- 현업 담당자는 맡은 문의함의 문의와 자기가 인수한 문의를 본다. IT는 협의 요청된 문의와 공통 오류를 본다.
- 관리자는 같은 지점 FC 범위만 보고, FC는 본인 문의만 본다.
- 범위 밖 문의는 주소로 직접 열어도 상세를 보이지 않는다.
- 백엔드 단계에서는 서버가 인증 세션으로 다시 검사한다.

## 대안(불채택)
- **새 화면·새 역할을 메뉴마다 만들기:** 일정·디자인 비용이 크다. 탭·필터·권한으로 나눈다.
- **문의 대응 상태 열 추가:** 기존 덧붙이기 기록에서 계산할 수 있고, 공통 오류 상태와 헷갈린다.
- **LLM 분류:** 실제 LLM이 연결되지 않아 검증할 수 없다. 규칙으로 먼저 하고 교체 지점만 둔다.
- **업무 코드 교체:** S5 시나리오·회귀 검사·저장된 시연 상태가 모두 바뀐다. 기존 코드에 상위 업무를 연결한다.
