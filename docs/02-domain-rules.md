# 02. 도메인 규칙 정의서

> 이 문서의 규칙은 **AI가 아니라 코드와 설정 파일(`config/*.yml`)로 구현**한다. 원천: 요청 5절, `proposal.md` 7.2.

## 1. 처리 등급
| 등급 | 조건 | 처리 |
|---|---|---|
| **즉시** | 청약·서명을 막는 결함, 또는 컴플라이언스 우려 | 바로 IT 이관 |
| **일반** | 로그인·접속 문제, 또는 여러 지점에서 반복 | 영업팀 임시조치 후 주간 검토 |
| **모아서** | 사용 불편, 개선 요청 | 월 단위 검토 |

### 판정 순서 (위에서부터 먼저 맞는 것)
1. 업무 = 청약·서명 **그리고** 증상 = 진행 불가 계열 → 즉시
2. 컴플라이언스 키워드(예: 서명, 동의, 설명의무, 잘못된 문서) 또는 담당자의 컴플라이언스 표시 → 즉시. 업무 = 고객동의·본인확인(ADR-027)이고 증상 = 진행 불가·입력 불가 계열이면 같은 이유로 즉시
3. 업무 = 로그인·접속 → 일반
4. 연결된 신고의 지점 수 ≥ 2 → **일반으로 상향 제안** (확정은 담당자)
5. 그 외 → 모아서
- 유형이 **사용법**이면 등급 없음(안내 후 종료).
- 컴플라이언스 판단은 **키워드 목록과 담당자 표시로만** 한다. AI는 판단하지 않는다.
- 키워드·임계값은 `config/grading-rules.yml`.

## 2. 유형
사용법 / 결함 / 개선. B모드에서는 AI 제안 + 사람 확인, A모드에서는 "미분류"로 두고 담당자가 확정.

## 3. 상태 단계
```
접수 → 재현 확인 → 원인 파악 → 임시조치 → 수정 예정(예정일 필수) → 해결
                         ↘ 수정하지 않음 (사유 필수) ↙  (어느 단계에서든 가능, 정상 종결)
```
- "수정하지 않음" 사유 코드: 신규 SFA에서 해결 / 우회법으로 충분 / 재현 불가 / 기타(자유 입력). 사유 없이는 저장 불가.
- [가정 G5] 상태는 앞으로 건너뛸 수 있다(예: 접수 → 임시조치). 되돌림은 사유를 남기며 알림 없음.
- "수정 예정"은 예정일 필수(되돌림으로 수정 예정이 되어도 같음).
- **해결과 검증(ADR-029).** `RESOLVED`는 해결이다. 해결 이력에 검증 기록(`verification`)이 있을 때만 "수정 완료"·"수정·배포 검증 완료"로 쓴다. 검증 시각은 적용 시각 이후이고 미래가 아니다. 프론트 단계의 검증은 모두 가상이다.
- **되돌림과 재배포(ADR-029).** 되돌림 사유는 코드(현장 문제 재검토·재배포 준비·잘못 기록·기타)로 저장한다. 재배포는 되돌린 뒤 다시 해결하며 새 해결 이력이 된다.
- **단계 표시(ADR-029).** 실제 기록된 단계만 보인다. 건너뛴 단계를 지나온 것으로 칠하지 않는다.

## 4. 알림 규칙
- **의미 있는 변경만** 알린다: 임시조치, 수정 예정(예정일 포함), 해결, 수정하지 않음(사유 포함) [가정 G4].
- 재현 확인·원인 파악·되돌림은 기록만 하고 알리지 않는다("확인 중" 반복 알림 금지).
- 상태는 **대표 결함 단위**로 한 번 바꾸고, 연결된 신고자 **전원**에게 전파(중복 수신자는 1회).
- 실제 발송 없음. 미리보기 + `NotificationLog` 기록만.
- 알림 본문은 승인된 안내문(`FcNotice.approvedText`) 우선, 없으면 고정 템플릿.

### 4-1. 받는 사람과 문구 (ADR-025)
- **받는 사람.** 위 알리는 변경이면 연결된 신고마다 ① 신고자(`reporterId`, 대상 `REPORTER`) ② 신고자와 다른 대리 접수자(`submittedById`, 대상 `SUBMITTER`). 한 변경에 한 사람은 1건이고, 같은 사람이 ①이기도 하면 ①만 받는다. ②는 그 사람이 대신 접수한 신고 수를 문구에 넣는다("대신 접수한 문의 N건").
- **대리 접수 알림.** 관리자가 FC 대신 접수·참여하면 FC에게만 접수 알림 1건(종류 `PROXY_RECEIPT`). 상태 변경이 아니므로 위 "의미 있는 변경만"의 예외이며, 대리 접수자 자신은 받지 않는다(완료 화면을 봄). 본문에는 업무 이름만 넣고 설명 원문은 넣지 않는다.
- **문구.** FC 문구는 "지금 할 일"을 먼저(임시 방법, 예정일까지 쓸 방법, 해결이면 기존 건 처리), 관리자 문구는 "FC가 업무를 이어갈 수 있는지 확인"을 먼저 쓴다. 고정 템플릿은 `statusTemplates`(FC)·`submitterTemplates`(관리자).
- **원칙.** 접수 완료 ≠ 담당자 확인(대표 결함에 연결돼야 "담당자가 확인했어요"), 임시조치 ≠ 근본 해결, 수정 예정 ≠ 수정 완료(예정일이 있을 때만 날짜), AI 추천 ≠ 같은 결함 확정, 같은 변경은 사람별 1건.
- **업무 재개 회신.** FC가 남긴 "진행했어요 / 아직 안 돼요"는 신고 단위 기록이다. 대표 결함 상태를 바꾸지 않고 알림도 만들지 않는다. "아직 안 돼요"는 그 신고의 후속 기록으로도 남는다.
- **AI 문의 중 임시 방법 결과(ADR-026).** 접수 전 AI 문의에서 고른 결과는 상담 결과일 뿐 기록이 아니다. FC가 자기 이름으로 접수하면 접수번호가 생긴 뒤 위 업무 재개 회신으로 기록하고, "지금은 확인할 수 없어요"는 접수 저장본에만 남긴다. 대리 접수에서는 관리자가 FC 대신 회신하지 않는다(저장하지 않음).
- **사실의 출처(ADR-026).** 접수에 붙은 발생 조건은 출처를 함께 둔다: FC가 알려 줌(`USER_REPORTED`), 접수 화면 자동 기록(`DEMO_CONTEXT`, 시연 진단), 브라우저 확인(`BROWSER_CAPTURED`, 백엔드 단계), 결함 대장 값(`DEFECT_LEDGER`), 미확인(`UNKNOWN`). 고객 휴대전화의 기기·로그는 FC 진술로만 남기고 자동 수집처럼 쓰지 않는다.

- **임시조치 상태(ADR-027).** 접수의 상담 결과는 임시조치 상태로 먼저 나눈다: 승인된 임시조치 없음(`NONE`) · 안내했지만 결과 미확인(`OFFERED`) · 시도함(`TRIED`). 결과(`RESUMED`·`STILL`)와 시도한 조치는 `TRIED`일 때만, "지금은 확인할 수 없어요"(`UNKNOWN`)는 `OFFERED`일 때만 남는다. 임시조치가 없으면 "아직 안 돼요"를 기록하지 않고, 업무를 이어가기 어려운지(추가 지원 필요 `supportNeeded`)를 따로 둔다. 대리 접수는 업무 재개와 같이 이 값도 FC 대신 정하지 않는다.
- **업무 재개 회신은 한 번(ADR-027).** 같은 신고·같은 신고자·같은 결과(또는 같은 요청)를 다시 받으면 새 기록·후속 기록을 만들지 않는다.
- **간편 알리기(ADR-027).** FC가 상담에서 안내받은 공개 결함과 "같은 오류예요"를 직접 확인하면 같은 오류 참여(`ME_TOO`)를 만든다. 이것은 FC의 참여이고 담당자의 신고 연결(REQ-LG-02)이 아니다. 같은 사용자가 그 결함에 이미 참여했거나 연결된 접수가 있으면 새로 만들지 않는다. AI가 스스로 참여시키지 않는다.
- **관리자의 FC 업무 상황(ADR-027, ADR-029로 고침).** 관리자 화면은 FC마다 **명시한 가장 최근 상황**(회신 또는 추가 지원 필요 예·아니요, 빈 신고는 앞선 상황을 덮지 않음)으로 ① 업무 재개(회신 `RESUMED`) ② 업무 진행 어려움(회신 `STILL` 또는 추가 지원 필요 `YES`) ③ 회신 없음(임시 방법이 있는데 답이 없거나 확인 전) ④ 임시조치 미확인(연결 전이거나 임시 방법이 아직 없음)으로 나눈다. 회신 없음은 업무 중단이 아니다.
- **수정 계획(ADR-027).** 신고가 늘어도 수정 예정일은 자동으로 정하지 않는다. 담당자가 기술 검토 뒤 [상태 바꾸기]에서 등록한다. 임시 방법이 없는 결함의 수정 예정 알림은 "안내된 임시 방법을 써 주세요" 대신 "임시 방법은 아직 없어요"로 채운다.

### 4-2. 수정 뒤 현장 확인 (ADR-029)
- IT의 해결과 FC의 확인은 따로다. 검증된 해결에만 확인을 받고, 답은 상태·알림을 바꾸지 않으며 해결의 조건도 아니다.
- 정상 진행(`CONFIRMED_OK`)·문제 지속(`STILL_FAIL`)·미확인(`NOT_TESTED` 또는 답 없음). 문제 지속만 후속 기록(`FIELD_FAIL`)을 남긴다. 재발·잔존 판단은 IT가 한다.
- 신고자 본인이면서 FC 역할일 때만(관리자·영업·IT는 본인 명의 신고에도 답하지 않는다), 신고·해결 이력별로 덧붙여 남긴다. 해결 이력이 바뀌면 미확인에서 다시 시작한다. 업무 재개 회신과 섞지 않는다.
- 사람 수는 FC별 최신 실제 답으로 세고(답 없는 다른 신고가 덮지 않음) 신고 수와 따로 쓴다. 둘 다 FC가 신고자인 신고만 센다.

### 4-3. 문의 단위 대응과 알림 (ADR-030)
- **두 단위.** 문의(`Report`)와 공통 오류(`Defect`)는 따로다. 공통 오류의 상태·전이·알림(3절·4절)은 그대로 두고, 문의는 결함으로 확인되기 전에도 대응할 수 있다.
- **문의 대응 기록.** 덧붙이기만 한다. 문의 대응 상태는 마지막 기록에서 계산하고 저장하지 않는다.

  | 기록 | 누가 | 뜻 | 화면 상태 |
  |---|---|---|---|
  | 분류(`ROUTE`) | 규칙 | 업무·문의함·근거 | 신규 |
  | 인수(`ASSIGN`) | 그 문의함 현업 담당자 | 담당 시작 | 확인 중 |
  | 추가 정보 요청(`INFO_REQUEST`) | 인수한 담당자 | 항목 코드 | 추가 정보 요청 → 문의자가 답하면 "추가 정보 도착" |
  | 대응 방법 안내(`GUIDE`) | 인수한 담당자 | 승인·공개된 공통 오류의 임시 방법 | 대응 방법 안내 |
  | 자체 해결(`SELF_RESOLVED`) | 인수한 담당자 | 처리 코드(사용 방법 안내로 해결·담당 부서에서 처리·안내한 방법으로 해결·다시 해보니 정상) | 처리 완료 |
  | IT 협의 요청(`IT_CONSULT`) | 인수한 담당자 | 질문 코드 | IT 협의 중 |
  | IT 협의 결과(`IT_REPLY`) | IT | 현장 안내 가능·IT 확인 계속·수정·배포 필요(ITGS 요청 필요)·재현 안 됨 | IT 회신 |
  | 재분류(`REROUTE`) | 담당자 | 새 문의함·사유 코드. 담당이 비워짐 | 신규(새 문의함) |

- **공통 오류 연결.** 공통 오류에 연결된 문의의 FC 화면 상태는 지금처럼 공통 오류 상태를 따른다.
- **인수.** 한 문의의 담당자는 한 명이다. 이미 다른 사람이 인수했으면 거부한다(`ALREADY_ASSIGNED`). 같은 사람의 같은 요청은 기존 기록을 돌려준다.
- **세 가지 확인.** 알림 읽음, 문의 확인(상세 열람), 인수는 따로 기록한다. FC 화면의 "담당자가 확인했어요"는 인수 또는 공통 오류 연결 뒤에만 쓴다(ADR-025 결정 2 변경).
- **대응 방법.** 안내할 수 있는 것은 승인·공개된 공통 오류의 임시 방법과 정해진 처리 문구뿐이다. 담당자가 현재 문의에 맞는지 판단해 고른다.
- **문의자 답.** 추가 정보 요청에는 문의자 본인만 선택형으로 답한다. 답은 출처 "FC가 추가로 알려 줌"(`USER_ADDED`)으로 붙고 앞선 값을 지우지 않는다.

**알림 (사람별 1건, 키 `eventId + recipientId + kind`)**

| 사건 | 받는 사람 | 종류 |
|---|---|---|
| 신규 문의(분류·재분류) | 그 문의함 담당자 | `NEW_INQUIRY` |
| IT 협의 요청 | IT 담당자 | `IT_CONSULT` |
| 추가 정보 요청 | 문의자 + 대리 접수자 | `INFO_REQUEST` |
| 대응 방법 안내·자체 해결 | 문의자 + 대리 접수자 | `INQUIRY_GUIDE` |

- 공통 오류에 이미 연결된 같은 오류 참여(간편 알리기)는 문의함에 보이지만 신규 문의 알림을 만들지 않는다.
- 관련 없는 문의함 담당자·IT·다른 지점에는 보내지 않는다. 앱 내부 알림만 만들고 실제 발송은 없다.
- 문제 지속 응답 알림(`FIELD_FAIL`)과 외부 채널 미리보기는 P1이다.

### 5-1. 담당 부서 매핑 (`config/department-map.yml`) — ADR-030 5-2절로 대체
업무·화면 → 부서. 초안:
| 업무 | 화면 예 | 담당 부서 |
|---|---|---|
| 로그인·접속 | 로그인 | 영업지원팀 (IT 인프라 협의) |
| 청약·서명 | 청약, 전자서명, 알림톡 | 청약업무팀 + IT |
| 고객조회 | 고객종합조회, 고객 목록 | 고객관리팀 + IT |
| 가입설계 | 가입설계 | 상품설계지원팀 |
| 계약조회 | 계약관리 | 계약관리팀 + IT |

### 5-2. 업무분장과 분류 (ADR-030, `js/fixtures/business-routes.js`)
- **업무분장(가상).** 상위 업무 8개 아래 기존 업무 코드를 세부 업무로 둔다. 항목은 업무 코드·업무명·상위 업무 코드·관련 화면 ID·문의함·IT 협의 영역·사용 여부다. **부서·문의함은 모두 가상 매핑**이며 실제 업무분장이 아니다.

| 상위 업무 | 세부 업무(기존 코드) | 관련 화면 ID | 문의함(가상) |
|---|---|---|---|
| 고객관리 | 고객조회 `CUSTOMER_LOOKUP` | `CUSTOMER_SEARCH` | 고객관리팀(가상) |
| 상품소개동의 | 고객동의·본인확인 `CUSTOMER_CONSENT` | `CONSENT_URL` | 고객동의업무팀(가상) |
| 가입설계 | 가입설계 `DESIGN` | `DESIGN` | 상품설계지원팀(가상) |
| 청약 | 청약·서명 `SUBSCRIPTION` | `SIGN_LINK`, `SUBSCRIPTION` | 청약업무팀(가상) |
| 심사 | (세부 코드 없음) | `UNDERWRITING` | 심사업무팀(가상) |
| 계약관리 | 계약조회 `CONTRACT_LOOKUP` | `CONTRACT` | 계약관리팀(가상) |
| 공통업무 | 로그인·접속 `LOGIN` | `LOGIN` | 영업지원팀(가상) |
| 기타 | 그 밖의 업무 `ETC` | — | 미분류 문의함 |

- **분류 순서.**
  1. FC가 고르거나 AI 문의에서 확인한 업무(`ETC` 제외)
  2. 오류가 난 화면 ID(진단 이벤트. 접수한 PC 화면은 쓰지 않음, ADR-028)
  3. 기존 이력(안내받은 공통 오류의 업무)
- **분류 결과.**
  - 근거들이 한 상위 업무를 가리키면 그 문의함으로 보낸다.
  - 서로 다른 상위 업무를 가리키면 공통 분류 문의함으로 보낸다.
  - 근거가 없으면 미분류 문의함으로 보낸다.
- **방식 표시.** 결과에는 근거 목록과 방식 `RULE`을 남긴다. 나중에 LLM 분류로 바꿔도 같은 결과 형식을 쓴다.

### 6-1. 접수 질문 우선순위 (ADR-030, ADR-026·027 유지)
AI 문의는 이미 아는 값을 묻지 않고 다음 순서로 묻는다. 확인 항목은 한 상담에 최대 3개다.
1. 지금 고객 업무를 이어갈 수 있는지(업무 진행 어려움)
2. 어느 단계에서 어떤 증상인지
3. 원인 분류·재현에 중요한 발생 조건
4. 이미 시도한 방법과 결과

모든 질문에 "잘 모르겠어요"가 있고, 언제든 지금까지의 내용으로 접수할 수 있다. 모르는 값은 미확인(`UNKNOWN`)으로 남는다.
S5 실험 경로(숫자 단계, 09번)의 질문은 바꾸지 않는다.
