# 02. 도메인 규칙 정의서

> 이 문서의 규칙은 **AI가 아니라 코드와 설정 파일(`config/*.yml`)로 구현**한다. 원천: 요청 5절, `proposal.md` 7.2.

## 1. 처리 등급
| 등급 | 조건 | 처리 |
|---|---|---|
| **즉시** | 청약·서명을 막는 결함, 또는 컴플라이언스 우려 | 바로 IT 이관 |
| **일반** | 로그인·접속 문제, 또는 여러 지점에서 반복 | 영업팀 임시조치 후 주간 검토 |
| **모아서** | 사용 불편, 개선 요청 | 월 단위 검토 |

### 판정 순서 (위에서부터 먼저 맞는 것)
1. 업무 = 청약·서명 **그리고** 증상 = 진행 불가 계열 → 즉시
2. 컴플라이언스 키워드(예: 서명, 동의, 설명의무, 잘못된 문서) 또는 담당자의 컴플라이언스 표시 → 즉시
3. 업무 = 로그인·접속 → 일반
4. 연결된 신고의 지점 수 ≥ 2 → **일반으로 상향 제안** (확정은 담당자)
5. 그 외 → 모아서
- 유형이 **사용법**이면 등급 없음(안내 후 종료).
- 컴플라이언스 판단은 **키워드 목록과 담당자 표시로만** 한다. AI는 판단하지 않는다.
- 키워드·임계값은 `config/grading-rules.yml`.

## 2. 유형
사용법 / 결함 / 개선. B모드에서는 AI 제안 + 사람 확인, A모드에서는 "미분류"로 두고 담당자가 확정.

## 3. 상태 단계
```
접수 → 재현 확인 → 원인 파악 → 임시조치 → 수정 예정(예정일 필수) → 해결
                         ↘ 수정하지 않음 (사유 필수) ↙  (어느 단계에서든 가능, 정상 종결)
```
- "수정하지 않음" 사유 코드: 신규 SFA에서 해결 / 우회법으로 충분 / 재현 불가 / 기타(자유 입력). 사유 없이는 저장 불가.
- [가정 G5] 상태는 앞으로 건너뛸 수 있다(예: 접수 → 임시조치). 되돌림은 사유를 남기며 알림 없음.
- "수정 예정"은 예정일 필수.

## 4. 알림 규칙
- **의미 있는 변경만** 알린다: 임시조치, 수정 예정(예정일 포함), 해결, 수정하지 않음(사유 포함) [가정 G4].
- 재현 확인·원인 파악·되돌림은 기록만 하고 알리지 않는다("확인 중" 반복 알림 금지).
- 상태는 **대표 결함 단위**로 한 번 바꾸고, 연결된 신고자 **전원**에게 전파(중복 수신자는 1회).
- 실제 발송 없음. 미리보기 + `NotificationLog` 기록만.
- 알림 본문은 승인된 안내문(`FcNotice.approvedText`) 우선, 없으면 고정 템플릿.

## 5. 결함 대장 필드
| 필드 | 설명 | 저장/계산 |
|---|---|---|
| 유형 | 사용법/결함/개선 | 저장 |
| 대표 결함 ID | 예: D-2026-001 | 저장 |
| 신·구 시스템 구분 | OLD / NEW | 저장 |
| 영향 지점 수 | 연결 신고의 서로 다른 지점 수 | **계산** |
| 연결된 신고 목록 | | 관계 |
| 처리 등급 | 1절 | 저장(규칙 제안 + 담당자 확정) |
| 상태 | 3절 | 저장 + 이력 |
| 담당 부서 | 5-1 매핑 | 저장 |

### 5-1. 담당 부서 매핑 (`config/department-map.yml`)
업무·화면 → 부서. 초안:
| 업무 | 화면 예 | 담당 부서 |
|---|---|---|
| 로그인·접속 | 로그인 | 영업지원팀 (IT 인프라 협의) |
| 청약·서명 | 청약, 전자서명, 알림톡 | 청약업무팀 + IT |
| 고객조회 | 고객종합조회, 고객 목록 | 고객관리팀 + IT |
| 가입설계 | 가입설계 | 상품설계지원팀 |
| 계약조회 | 계약관리 | 계약관리팀 + IT |
| 기타 | | 영업지원팀 |
> 부서명은 가상. 실제 부서명은 영업팀 검토 때 교체(미결, 11/13).
