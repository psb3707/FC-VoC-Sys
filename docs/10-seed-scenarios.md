# 10. 시드 데이터·시나리오·정답표

> 모든 데이터는 **가상**. 실제 고객 정보, 사번, 설계번호를 넣지 않는다. `references/` 값 복사 금지.
> 이 문서는 구조와 목록을 정의하고, 카드 문장·정답표 상세는 11/13까지 영업팀 검토를 거쳐 채운다.

## 1. 시드 규모
| 데이터 | 규모 | 내용 |
|---|---|---|
| 지점 | 5 | 가상 지점명 |
| 사용자 | FC 8, 관리자 3, 영업팀 2, IT 2 | 고령 FC 페르소나 포함, 이름은 명백한 가상 |
| 가상 계약 | 10 | K-01 시연용 1건 포함, 상태·상품군·변경 다양 |
| 대표 결함 | 5 | 현장 사례 3건 + 알려진 오류 2~3건(공개·우회법 포함), 상태 다양 |
| 신고 | 12~15 | 결함당 1~5건, 지점 분산, "수정하지 않음" 1건 포함 |
| 사용법 시나리오 | 2 | 예: 비밀번호 재설정, 출력 방법 |
| 평가 데이터 | | 마스킹 말뭉치, 분류 정답 20건 (08·11번) |
- 번호 형식은 숫자 위주 가상 값. 실제 체계를 재현하지 않는다 [G3].
- 시드는 코드가 아니라 `seed/*.yml`. 자동 테스트로 주민번호 형식 등이 시드에 없는지 검사.

## 2. 필수 포함 사례
| # | 사례 | 등급 | 비고 |
|---|---|---|---|
| ① | 알림톡 링크 오연결: 세미나 초대장 발송 이력이 있는 FC가 청약 서명 알림톡을 누르면 초대장으로 연결 | **즉시** | 핵심 조건 = 초대장 발송 이력. 모바일 가능성 [Q4] |
| ② | 로그인 입력 오류: 문자는 b, 숫자는 1만 입력됨 | 일반 | |
| ③ | 고객 목록 클릭 오류: 상세 조회를 위해 이름이 아닌 성별을 눌러야 함 | 모아서(사용 불편) | |
| 고객 | 특정 고객의 가입내역이 조회되지 않음 | (시연 대본으로 확인) | 마스킹·참조키·속성 전달 시연. 제안서 7.5 흐름 |
| 사용법 | 사용법 문의 1~2건 | - | 사용법 분류 → 안내 후 종료 확인 |
고객 건 시연 흐름(제안서 7.5): 입력 → 마스킹 → 자동 수집(화면, 오류코드, 시각) → 속성 전달 → AI 판단(되묻기 "다른 고객도 같은 증상이 있나요?", 안내문 초안) → 담당자가 참조키로 사내 시스템에서 확인. **담당 부서는 7.5와 달리 규칙이 정한다.**

## 3. 실험 시나리오 세트 (쌍 구조: 같은 번호끼리 난이도·업무를 맞춤)
| 쌍 | S1 | S2 | 난이도 |
|---|---|---|---|
| 1 | 알림톡 링크 오연결 (사례 ①) | 청약 서명 링크가 만료 안내로 연결 | 높음 |
| 2 | 로그인 입력 오류 (사례 ②) | 공인인증 화면 키패드 오입력 | 중간 |
| 3 | 고객 목록 클릭 오류 (사례 ③) | 계약 목록 정렬 후 상세 불일치 | 중간 |
| 4 | 특정 고객 가입내역 미조회 | 특정 고객 납입내역 미조회 | 높음 |
| 연습 | 인쇄 버튼 무반응 | 첨부 메뉴 표시 깨짐 | 낮음 |
- 사용법 시나리오는 실험 세트에 넣지 않는다(09번).
- 쌍 난이도 동등성은 파일럿 2명의 시간·누락 수로 점검, 필요 시 카드 수정.

## 4. 시나리오 정의 형식 (`seed/scenarios.yml`)
```
id: S1-1
set: S1
pairNo: 1
practice: false
cardText: (FC의 상황 이야기. 항목 나열 금지. 무관한 정보 일부 포함)
simulatedContext: {screen: ..., device: ..., browser: ..., occurredAt: ...}   # 자동 수집 값
customerNo: (고객 관련일 때만, 가상 값)
answerKey:
  - {code: SCREEN, label: 화면, manual: false}
  - {code: DEVICE, label: 기기, manual: false}
  - {code: PATH, label: 재현 경로, manual: true, accept: [...], reject: [...]}
  - {code: SYMPTOM, label: 증상, manual: true}
  - {code: KEY_CONDITION, label: 핵심 조건(예: 초대장 발송 이력), manual: true}
```
항목 구성은 제안서 6.1(화면·기기·경로·증상) + 시나리오별 핵심 조건. `accept/reject`로 인정·불인정 예시를 둔다.

## 5. 알려진 오류 (실험 외 시연용)
2~3건, 각각 제목, 임시 우회법, 수정 예정일 또는 "수정하지 않음" 사유 샘플. 사례 ②(쿠키 삭제 후 재접속 같은 임시방편 vs 근본 수정 구분)를 포함.

## 6. 평가용 데이터
- `eval/masking-dev.yml`(30건+), `eval/masking-holdout.yml`(10건+, **동료 작성**, 개발 중 열람 금지, 12/2 1회 실행), 과잉 마스킹용 업무 문장 15건.
- `eval/classification-gold.yml` 20건: 사용법/결함/개선 정답 라벨.

## 7. 검토 체크리스트 (수작업)

- [ ] 영업팀 담당자가 시나리오 현실성·부서명 확인
