# 문의 맥락 분류·담당 그룹 연결·접수 완료 화면 — 현황 분석과 변경 계획 (TASK 00)

- 상태: 검토 완료 (2026-11-28). ADR-031 승인과 사용자 선택(기존 코드 유지 + 추가, 업무 선택은 선택 사항, 인수 뒤 담당자 이름·가상 내선 표시)을 반영했다. 근거 지시서: "FC-VoC-Sys — 업무 자동 분류·담당자 매핑·접수 완료 화면 고도화"
- 기준: `main` `28595df` (#29 ADR-030 반영). 단계 `FRONTEND`
- 관련 결정: [ADR-030](../adr/ADR-030-business-routing-handling-workflow.md)(승인), [ADR-031](../adr/ADR-031-context-classification-contact-routing.md)(승인)

## 1. 확인한 규칙과 전제
- **우선순위:** 승인된 ADR > `docs/00~12` > 지시서. 지시서가 승인 ADR과 다른 곳은 ADR-031로 바꾼 뒤에만 구현한다(4절).
- **단계:** `FRONTEND`. 바꿀 수 있는 곳은 `src/main/resources/static/**`, `docs/`, `scripts/`다. 데이터·API는 지금처럼 `api-client.js` + `js/fixtures/` + 브라우저 저장소(`IntakeDemoStore`)로 만든다.
- **실제 LLM 없음.** 문장 분류는 규칙(낱말 묶음·오타 허용·충돌 판단)이다. 화면과 보고에 "규칙으로 분류"라고 쓰고, 정확도 확률을 만들지 않는다.
- **원문 보관.** 자유 입력 원문은 페이지 메모리(ADR-021)다. 분류는 접수하는 순간 페이지 안에서 하고, 저장하는 것은 업무 코드와 근거 코드(어느 규칙 묶음이 맞았는지)뿐이다.
- **가상 데이터.** 부서·담당 그룹·IT 그룹·내선 번호는 모두 가상이고 "(가상)"으로 표시한다.

### 2-1. 지시서가 물은 것에 대한 답
- **업무 분류가 사용자 선택에만 의존하는가?** 사실상 그렇다. 빠른 접수는 업무 선택이 필수이고(`intake-quick.js` "어떤 업무인지 골라 주세요"), 분류는 그 값을 먼저 쓴다. 화면 ID는 진단 이벤트가 있을 때만 쓴다.
- **자연어로 업무를 추론하는 로직이 있는가?** 알려진 결함 7건과 맞춰 보는 것만 있다. 업무 분류용 낱말 규칙은 없다.
- **현업부서 전달과 개인 배정이 나뉘어 있는가?** 나뉘어 있다(문의함 전달 → 인수). 다만 담당 그룹 연락처와 실제 처리 담당자를 화면에서 나눠 보이지 않는다.
- **IT 협의가 모든 IT 담당자에게 가는가?** 그렇다. 지금은 IT가 1명뿐이라 드러나지 않았다.
- **기존 문의번호로 담당자가 상세를 볼 수 있는가?** 내 문의함이나 내가 인수한 문의면 된다. 다른 문의함이면 찾기 결과가 비고 이유를 알 수 없다.

## 3. 바꾸지 않는 것
- ADR-030의 문의함 전달 → 인수 → 현업 대응 → IT 협의 → ITGS 초안(복사만) 흐름과 대응 기록 6종
- 공통 오류 상태 7종·연결은 사람(ADR-017)·자유 입력 원문은 페이지 메모리(ADR-021)·신원 검증(ADR-028)·현장 확인(ADR-029)
- 기존 업무 코드 7종·내부 필드·주소 키. 기존 시드·시연(고객 동의 키패드, 전자서명)과 회귀 검사
- S5 실험 경로(09번): 숫자 단계 주소의 S2 접수는 업무를 그대로 고른다(측정 조건 유지)

## 5. 변경 계획

### 5-1. 데이터 (`fixtures/business-routes.js`·`users.js`, 05번 1절)
- **세부 업무 추가:** `PRE_UW`(선심사), `UW_NEW`(신계약심사), `APPLICATION`(청약서 작성·제출), `E_SIGN`(전자서명). 기존 `SUBSCRIPTION`(청약·서명)은 "청약 전반"으로 남겨 기존 접수·시연이 그대로 간다.
- **상위 업무:** 고객관리 · 상품소개동의 · 가입설계 · 선심사 · 청약 · 신계약심사 · 계약관리 · 공통업무 · 기타(업무 미확인)
- **업무 표현(`lexicon`):** 세부 업무마다 대상 낱말 묶음(예: 보험료·계산·설계), 동작 낱말, 대표 증상, 오타 변형. 문장 하나에서 대상 낱말과 동작·증상이 함께 맞아야 근거로 친다.
- **모호 규칙(`ambiguities`):** "심사 결과" → 선심사/신계약심사 질문, "제출 버튼" → 청약서/선심사/기타 질문, "서명" → 전자서명은 오류 단계(청약 서명·동의 서명)로 질문.
- **담당 그룹(`inboxes` 확장):** 업무 연락처 `{label, ext}`(가상 내선), `backupInboxId`, `active`
- **IT 담당 그룹(`itGroups` 신규):** 영역(`itArea`)별 그룹, 공통 IT 협의함 `ITG-COMMON`
- **사용자:** `contact`(가상 내선), `primary`, `active`, `available`(인수 가능), IT는 `itGroupIds`. IT 가상 사용자 추가(청약·가입설계·공통). 기존 U-030은 고객동의 IT로 두어 기존 시연·회귀가 그대로 간다.

### 5-2. 규칙·API (`api-client.js`, 05번 3절)
- `classifyText(text)`(페이지 안): 문장 → 업무 후보와 근거 코드. 원문은 저장하지 않는다.
- `classify(r)`: 근거 ①고른 업무 ②FC 확인 응답 ③오류 화면 ID ④문장 규칙 ⑤이력. 결과에 `confirmed`·`basis`·`needs`(추가 확인)·`question`(물어볼 것 하나)
- `routeTarget(route)`: 담당 그룹 → 사용 중 구성원이 없으면 대체 그룹 → 공통 분류 문의함
- `itGroupOf(route)`: `itArea` → IT 그룹 → 없으면 공통 IT 협의함
- `getIntakeRouting(req)`: 접수 전 확인 화면용 분류 미리보기
- `claimConsult(reportId, userId)`: IT 협의 인수(현업 인수와 별도 기록)
- `findInquiryByNumber(id, userId)`: 범위 밖이면 전달된 문의함 이름만
- 대응 기록 `PHONE`(전화 대응, 코드만) 추가

### 5-3. 화면
- **AI 문의·빠른 접수:** 업무 선택은 선택 사항. 모호하면 질문 하나(선택지 + "잘 모르겠어요"). 확인 화면에 "○○ 업무 관련 문의로 확인했어요" + [업무 바꾸기]
- **접수 완료:** 결과 문장 2줄, 문의 정보 표(문의번호·관련 업무·세부 업무·담당 부서·처리 상태), 업무 지원 연락처(가상), 버튼 [문의번호 복사]·[내 문의 및 처리 경과]·[업무 지원 연락처]·[닫기]
- **내 문의 카드:** 상태별 담당자 표시(인수 전 "담당자 확인 대기 중", 인수 뒤 이름·업무 연락처, IT 협의 중에도 현업 지원 경로)
- **현업 문의 상세:** 분류 근거(문장 규칙·화면·확인 응답)·미확인, IT 담당 그룹·협의 담당자·업무 연락처, [전화 대응 기록]
- **IT 협의 요청:** 내 IT 그룹만, [협의 맡기]
