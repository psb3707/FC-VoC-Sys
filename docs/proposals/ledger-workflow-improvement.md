# 기존 결함 대장 개선 계획

- 작성일: 2026-11-10
- 계획 보완: AI 기능의 화면·시연 흐름을 1차 개선 범위에 포함한다.
- 대상: `src/main/resources/static/ledger.html` 및 연결된 화면·데이터 계약
- 상태: 논의 내용을 종합한 검토용 계획. 기존 승인 ADR·요구사항을 대체하지 않는다.
- 이번 산출물은 계획만 포함한다. 화면 구현·PHASE·기존 상태 코드는 변경하지 않는다.

## 1. 목표와 사용자

화면의 목적을 ‘대표 결함에 신고 연결’에서 ‘업무별 문의·오류를 공동으로 확인하고 대응 결과를 공유’로 확장한다.

확인된 전달 경로는 FC → 지점장·부지점장 → 영업팀·영업관리자 단톡방 → 필요 시 IT 협조다. 주요 화면 사용자는 영업팀·영업관리자·IT로 설정한다. 지점 관리자의 직접 사용 여부와 실제 업무별 담당 명단은 구현 전 확인한다. 로그인·운영 권한 구축은 이번 PoC 범위에 추가하지 않는다.

검증 질문:

1. 사용자가 자기 업무에서 지금 확인할 건과 다음 행동을 찾을 수 있는가?
2. 기존 사례가 없는 새 문의도 추가 확인·이관·안내 종료까지 처리할 수 있는가?
3. 내부 확인 내용과 현장 전달 내용을 구분하여 기록할 수 있는가?
4. 과거 사례를 찾아 적용 조건을 확인하고 이번 건에 활용할 수 있는가?

## 2. 원칙과 범위

- 기존 디자인 토큰·한국어·큰 글씨·키보드 조작을 유지한다. 정보량을 줄이기 위해 글씨와 버튼을 작게 만들지 않는다.
- 반복 안내·중복 상태 표시를 줄여 업무 영향·담당·다음 조치로 교체한다.
- 업무 분류, 처리 책임, IT 협조, 처리 상태, 현장 공유 여부를 구분한다.
- 접수 1건과 여러 접수를 묶는 관리 건을 구분한다. 참고 사례 연결은 동일 문제 연결과 별개다.
- 신규 접수는 기존 오류에 연결하지 않아도 처리할 수 있어야 한다.
- 화면 검증은 가상 데이터로 한다. 실제 AI 호출·영구 저장·보안 경계 검증은 BACKEND 단계의 별도 범위다.
- AI 진입점과 질문·답변·근거 확인·후보 비교는 1차 화면 개선부터 제공한다. 실제 처리 기록 축적이나 대응 흐름 전체 완성을 기다리지 않고 가상 사례·고정 응답으로 시연한다. 실제 AI 품질 검증과 화면 사용성 검증은 구분한다.
- 로그인, 조직도 연동, 단톡방 자동 수집·발송, SLA 자동화, 운영 배포, 통계 대시보드는 제외한다.
- 기존 접수 A/B 실험의 목적과 조건은 유지한다. 이번 관리자 화면 평가는 별도 과업 평가다.

## 3. 정보 구조

표시 이름은 ‘업무 문의·오류 관리’를 제안한다. `ledger.html` 경로는 유지한다.

```text
업무 문의·오류 관리                     검색 / 사례에 물어보기
업무: 전체 / 가입설계 / 청약 / 고객관리 / 계약관리 / 공통 / 업무 확인 필요

검토 대기 접수 | 진행 건 | 처리 사례
선택 목록의 빠른 조건: 내가 확인할 건 / 전체
상황 조건: 추가정보 대기 / 재확인 필요 / 확인일 경과

문제 | 업무·세부 단계 | 영향·현재 상황 | 담당·다음 조치
```

‘내가 확인할 건’은 목록과 같은 수준의 탭으로 중첩하지 않고 빠른 조건으로 둔다. 검토 대기 접수는 개별 접수, 진행 건은 관리 단위, 처리 사례는 완료된 기록을 보여 준다. 숫자는 선택한 업무·조건과 같은 범위에서 집계한다. 목록 간 전환 시 적용 조건을 명시하고, 지원하지 않는 조건을 숨겨진 채 유지하지 않는다.

기본 진입은 선택 사용자의 담당 업무에서 ‘검토 대기 접수’를 연다. 업무와 조회 조건은 주소에 보존하되, 상세 설명·내부 메모·공유 초안 등 입력 내용은 주소에 넣지 않는다.

### 목록

- 제목과 업무 단계, 업무 중단·마감·우회 가능 여부를 앞세운다.
- 지점 수와 신고 수는 ‘3개 지점 · 접수 4건’으로 통합한다. 발생 규모의 참고치이며 전체 영향 범위로 단정하지 않는다.
- 유형·신구 시스템은 상세와 선택 필터로 이동한다.
- 완료·종료 건은 기본 진행 목록에서 제외한다.
- 기본 정렬: 수동 긴급 확인 지정 → 다음 확인 시점 경과 → 오래 대기한 건. 동일 조건에서는 접수 시각과 ID로 고정 정렬한다.
- 긴급 확인 이유를 표시한다. 업무 중단·당일 마감·데이터 이상 가능성은 담당자가 판단할 근거로 제공하며, AI가 긴급도를 확정하지 않는다.
- 화면을 봤다는 사실과 처리 착수·담당 배정을 구분한다. 새 표시를 지워도 미처리 건이 사라지지 않는다.

### 상세

1. 문제·업무 영향·발생 시각
2. 주 담당자·협조 담당·다음 조치·다음 확인일
3. 현장 공유 내용과 마지막 공유 확인 시각
4. 발생 상황·확인 사실·미확인 사항
5. 관련 사례·관련 접수·전체 이력·진단정보

상단은 짧은 업무 요약, 하단은 펼쳐 보는 근거로 구성한다. 고객 진술·설계사 확인·담당자 확인·AI 추정을 구분한다. 기존 상세 설명·긴급 사정·연락 희망 등 접수 데이터가 상세에서 누락되지 않는지 확인한다.

전체 접수와 이력은 기본 접힘으로 두되 재발·우회법 실패·긴급 사정 추가는 상단 ‘새 확인 사항’에 노출한다. 처리 완료 후 재발은 원 관리 건에 재검토 표시를 추가하고 명시적으로 담당자를 지정한다. 단순 추가 접수만으로 자동 재오픈하지 않는다.

기본 읽기는 넓은 상세 패널을 사용하고, 비교 시에는 목록 대신 신고와 후보를 나란히 보여 준다. 후보 상세를 열기 위해 대화상자를 연속 중첩하지 않는다. 화면 폭이 좁으면 단일 상세로 전환한다.

## 4. 업무 분류와 책임

| 항목 | 계획 |
|---|---|
| 주 업무 | 가입설계·청약·고객관리·계약관리·공통·확인 필요. 실제 업무 분장에 맞춰 확정 |
| 세부 업무 | 청약의 전자서명, 가입설계의 보험료 계산 등 필요한 범위만 |
| 관련 업무 | 다부서 문제의 협조 범위. 주 업무는 하나 유지 |
| 현재 책임자 | 현장 회신과 진행을 책임지는 사람 1명 |
| IT 협조 담당 | 주 업무의 기본 협조 담당을 제안하되 사람이 요청·변경 |
| 다음 조치 | 구체적 행동과 확인 시점. 수정 예정일과 별도 |

알림톡 오류처럼 공통 기술이 관련돼도 발생 업무가 청약이면 주 업무는 청약으로 유지할 수 있다. 업무 변경 시 담당 변경 필요 여부를 확인한다. 다른 업무로 이관한 뒤 건이 사라지지 않도록 결과와 새 담당을 보여 준다.

## 5. 처리 행동과 상태

| 행동 | 최소 입력·결과 |
|---|---|
| 기존 관리 건에 연결 | 후보 비교, 연결 근거, 현재 안내 내용 확인 |
| 새 관리 건 등록 | 제목·업무·담당자·첫 조치. 입력 내용 재사용 |
| 추가정보 요청 | 필요한 질문·요청 대상·요청 시각·다음 확인일 |
| 안내 후 종료 | 실제 안내 내용·종료 사유 |
| 담당 변경·IT 협조 요청 | 확인 내용·협조 질문·회신 희망 시점·수신 담당 |
| 연결 해제·재연결 | 변경 사유·대상·이력. 복사된 정보와 공유 대상의 변화 확인 |
| 재검토 | 재발 근거·담당자·다음 조치 |

상태는 ‘검토 대기 / 확인 중 / 추가정보 대기 / 조치 중 / 처리 완료’를 후보로 삼는다. 최종 확정 전 기존 RECEIVED~WONT_FIX 상태와 매핑 표를 작성하고, 기존 FC 화면·알림·상태 이력과의 호환 여부를 확인한다. 단순 문자열 치환으로 적용하지 않는다.

IT 협조 여부·우회법 존재·조치 예정·현장 회신 여부는 보조 속성으로 관리한다. ‘재현 안 됨’은 즉시 종료 사유로 확정하지 않는다. ‘수정하지 않음’은 안내 완료·현행 유지·차기 반영 등 실제 판단으로 분해하고, 최종 결정과 사유를 함께 기록한다. 차기 반영이 확약됐는지 검토 중인지 구분한다.

## 6. 현장 공유와 기록

- ‘FC 안내문’의 관리자 화면 이름은 ‘현장 공유 내용’으로 바꾼다.
- 현재 상황·지금 할 일·적용 조건·다음 안내 시점 중심의 초안을 제공한다.
- 내부 메모와 분리하고 사람이 확인한 문구만 복사 가능하게 한다.
- 복사는 발송·전달 완료로 처리하지 않는다. 담당자가 별도로 공유 완료를 기록한다.
- 기존 SFA 알림·FC 게시 경로는 제거하지 않는다. 기존 승인본과 새 공유본의 관계를 ADR에서 정하고 기존 경로 회귀 검증을 수행한다.
- 기존 건 연결 직후 우회법을 바로 공유할 수 있게 한다. 다음 상태 변경까지 기다리게 하지 않는다.
- 처리 완료 시 조치 결과와 확인 근거를 한 줄 남긴다. 실제 확인 완료와 확인하지 못한 상태를 구분한다.
- 입력 중 목록 이동·닫기를 할 때 작성 내용이 유실되지 않도록 보존하거나 경고한다. 저장·복사 실패에는 재시도 경로를 제공한다.

## 7. 자연어 사례 검색

구현 보완(ADR-024): 표시 이름은 ‘이전 처리 방법 찾기’, 열린 영역은 ‘어떻게 대응하면 될까요?’로 한다. 답변은 사례별 표 나열 대신 핵심 답·확인 사항·조건별 행동·근거로 구성한다. 다른 증상과 세부 근거는 접고 모호한 질문은 짧게 되묻는다. 특정 접수에는 사람이 확인할 현장 안내·확인 요청 초안을 제공한다. 아래의 ‘사례에 물어보기’는 초기 계획 명칭이며 현재 표시 문구는 이 보완을 따른다.

일반 글자 검색과 ‘사례에 물어보기’를 구분한다. 선택 업무 범위를 기본으로 사용하고 전체 업무 확장 여부를 명시한다.

### 1차 화면에 포함할 AI 경험

- 목록 머리에 ‘AI 사례에 물어보기’를 항상 찾을 수 있게 둔다. 빈 화면에서는 ‘서명 오류는 전에 어떻게 처리했어?’ 같은 예시 질문을 제공한다.
- 질문하면 별도 AI 영역이 열리고 업무 범위, 질문, 답변 요약, 관련 사례, 적용 조건·차이점, 추가 확인 사항을 보여 준다. AI 영역은 사용자가 열 때 확장하며 목록을 상시 밀어내지 않는다.
- 답변에서 근거 사례 상세를 열고 ‘참고 사례로 연결’할 수 있는 흐름을 가상 데이터로 제공한다. 연결 여부는 사람이 결정한다.
- 접수 상세에도 ‘유사 사례 보기’를 제공한다. 기존 AI 후보 추천은 유지하되 업무 영향·신고 근거보다 아래에 배치하고 후보 비교로 연결한다.
- 초기 시연용 성공·검색 결과 없음·조건 불일치·오래된 조치·지연·실패 응답을 준비한다. 지연·실패 시 직접 검색과 수동 처리를 계속할 수 있게 한다.
- 질문 입력·전송, 고정 답변 확인, 근거 열기, 후보 비교까지 실제 클릭으로 이어지게 한다. 버튼만 배치하거나 설명 문구만 보여 주는 상태는 완료로 보지 않는다.
- AI 답변은 참고임을 짧게 표시한다. 고정 응답 기반 화면 시연이라는 점은 기존 ADR-016에 따라 발표·검토 설명에서 명시하고, 실제 AI 성능을 검증한 것으로 보고하지 않는다.

AI 현장 공유 초안·추가질문 생성·메시지 붙여넣기 초안은 후속 선택 범위다. 1차 필수 AI 경험은 사례 질문과 유사 사례 추천에 집중한다.

필수 답변 요소:

- 관련 사례와 원문 링크, 처리 시점, 현재 유효 여부
- 동일한 조건과 다른 조건, 실제 조치와 확인된 결과
- 이번 건에서 추가 확인할 내용
- 근거 부족·검색 결과 없음·서로 다른 기록의 충돌 표시

AI는 원인·해결을 확정하거나 자동 연결하지 않는다. ‘참고 사례로 연결’과 ‘기존 관리 건에 연결’은 별개다. 추천 기준·송신 범위는 펼침으로 제공한다. 삭제되거나 접근할 수 없는 근거를 이용해 답변하지 않는다.

FRONTEND 1차에서는 소수의 충실한 가상 사례와 고정 응답으로 위 흐름을 시연한다. 3단계에서는 대응 흐름에서 남기는 기록과 사례 표시의 일관성·검색 시나리오 범위를 보강하고, 실제 검색 품질은 BACKEND 단계에서 검증한다. 벡터 DB 도입을 선행 조건으로 삼지 않는다. 실제 호출 시 서버의 마스킹·허용 필드·출력 검증 경계를 유지한다.

## 8. 단계별 실행

| 단계 | 작업·산출물 | 완료 조건 |
|---|---|---|
| 0. 기준선 | 제안 ADR, 01·02·05·06·07·08·11·12 영향 정리, 용어·상태 매핑, 가상 사례·AI 고정 응답 정의 | 기존 기능의 유지·변경·보류와 AI 시연 범위가 추적 가능 |
| 1. 목록·상세·AI 시연 | 업무별 조회, 접수·진행·사례 분리, 핵심 정보 배치, 반복 설명 축소, AI 질문·답변·출처·유사 후보 비교 | 자기 업무·지금 할 일·근거를 찾고, AI 질문부터 사례 확인까지 클릭으로 시연 가능 |
| 2. 대응 흐름 | 신규 등록·안내 종료·추가 요청·이관, 다음 조치, 현장 공유, 재검토 | 신규 문의 1건을 접수부터 결과 기록까지 완결 |
| 3. 사례 활용 보강 | 대응 기록과 사례의 연결, 업무별 질문·비교 시나리오 확장, 기존 AI 화면 개선 | 적용 가능한 사례와 유사하지만 다른 사례를 구분하고 기록과 근거가 일치 |
| 4. 실제 연결 | 별도 BACKEND 작업으로 AI 호출·저장·송신 통제·실험 기록 연결 | 실제 API·실패 대체·감사 검증 통과 |

0~2를 우선 범위로 하며 AI 화면 시연은 1에 포함한다. 3은 사례 기록과 2의 완료 후 수행하는 보강 작업이며 AI 기능의 최초 노출을 늦추는 조건이 아니다. 일정이 부족하면 메시지 붙여넣기 초안·AI 추가질문 생성·개인 기본 설정을 보류하되, AI 사례 질문·근거 확인·유사 후보 비교와 핵심 대응 경로는 유지한다. 실제 담당자 수·상태 합의·기존 코드 영향 확인 전 확정 공수는 제시하지 않는다.

## 9. 변경 대상과 회귀 범위

- 화면: `ledger.html`, `js/ledger.js`, `css/ledger.css`. 공용 토큰과 접근성 기준 유지.
- 데이터 창구: `js/api-client.js`만 사용. fixtures, `intake-demo-store.js`, 진단·첨부·후속 접수와의 공유 계약 점검.
- 검증 도구: 새 탭·상태 구조에 맞춰 자체 검사와 `scripts/ui_check.py`의 의미 있는 항목을 갱신한다. 현재 탭 2개 등 구조 고정 검사만 통과하도록 맞추지 않는다.
- 기존 SFA 접수·알려진 오류·내 신고·상태 알림·해결 안내·첨부 열람·알림 재시도는 회귀 대상이다.
- 업무·상태·담당 정보의 구 데이터 기본값과 전환 계획을 정의한다. 개발용 초기화와 실험 데이터 보존을 구분한다.
- 사용자 역할 전환은 PoC 시연 장치이며 실제 접근 통제를 검증했다고 주장하지 않는다.

## 10. 사용자 검증 시나리오

1. 청약 신규 접수: 영업 담당이 영향 확인 → 청약 IT 협조 요청 → 결과 기록 → 공유 문구 확인·복사 → 공유 완료 기록.
2. 사용법 문의: 추가 확인 → 안내 → 종료. 결함 생성 없이 완료 가능.
3. 기존 오류 반복: 조건 비교 → 기존 건 연결 → 현재 우회법 안내.
4. 유사하지만 다른 오류: AI 후보의 차이 확인 → 신규 건 등록.
5. 처리 완료 뒤 재발: 재확인 필요 노출 → 담당 지정 → 근거 확인 → 재검토.
6. 다업무 문제: 주 업무·협조 업무 지정 → 이관 → 회신 책임 유지.
7. AI 없음·실패·오래된 사례: 근거 한계를 확인하고 직접 조사 진행.
8. 입력 중 이동·저장 실패·잘못된 연결: 내용 보존·재시도·복구 가능.
9. 1차 AI 시연: 업무 선택 → 예시 질문 또는 직접 입력 → 고정 답변·출처 확인 → 사례 상세·조건 비교 → 참고 연결. 결과 없음·지연·실패에서 수동 처리로 이동 가능. 화면 흐름만 평가하고 모델 품질은 평가하지 않는다.

영업·IT 역할을 포함하는 소규모 형성 평가를 수행한다. 기존 화면과 같은 과업으로 비교하고 진행자 도움 없이 완료 여부, 필요한 정보 탐색 시간, 잘못된 연결·누락, 외부 메모 필요 여부를 기록한다. 수치 목표는 예비 평가 후 본 평가 전에 고정한다. 기본 수용 기준은 업무·담당·다음 조치 식별, 신규 접수의 막힘 없는 처리, 공유와 내부 기록 구분, AI 근거 확인이다.

## 11. 구현 전 확인 항목

- 실제 업무 영역·세부 단계·IT 담당 매핑: 없으면 가상 명단으로 화면 검증하되 실제 조직 분장으로 주장하지 않는다.
- 영업관리자와 영업팀의 배정·종료 책임: PoC는 현재 책임자 1명을 명시하는 방식으로 시작한다.
- 지점 관리자 직접 사용 여부: 초기 화면은 영업·IT 중심으로 설계한다.
- FC 직접 알림 유지 범위: 기존 동작은 보존하고 공유 문구 경로부터 추가한다.
- 상태 변경과 원 접수·관리 건·공개 안내의 관계: ADR·데이터 계약에서 먼저 확정한다.

다음 실행 단위는 ‘0. 기준선 및 화면 설계’다. 이 계획을 곧바로 제품 요구사항 승인이나 백엔드 전체 구현 지시로 해석하지 않는다.
