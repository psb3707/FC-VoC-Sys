# 신고 → 업무 요청 → 시스템 로그 추적 설계안 (P1, 구현 제외)

> 상태: **제안(미확정)** · 작성 2026-11-21 · 기준: ADR-028(신고자 정보 자동 연결과 접수·발생 환경 진단)
> 이 문서는 **기준 문서가 아니다.** 실제 업무 시스템이 아래 이벤트를 기록하는지, 어떤 식별자를 쓰는지는 **확인 필요**다. 채택한 항목만 ADR → 문서 수정 → 구현 순서로 옮긴다(00번 5절). 이번 PoC에는 운영 로그 조회 API·수집 기능을 만들지 않는다.

## 1. 목적과 경계
- IT 담당자가 신고 한 건에서 "누가·언제·어느 화면에서·어떤 업무 요청을 하다가" 문제가 났는지 따라가 관련 로그를 **요청**할 수 있게 한다.
- 이 PoC가 하는 일은 추적에 필요한 **정확한 단서를 접수 단계에서 확보**하는 것까지다(ADR-028: 신고자·접수자 ID, 접수 시각, 화면 코드, 접수 환경, FC가 알려 준 발생 조건). 로그 조회·분석·원인 판단은 IT 담당자와 운영 시스템의 몫이다.
- 고객 휴대전화에서 키패드가 안 뜨는 현상은 **브라우저 안에서만** 일어날 수 있어 서버 로그에 남지 않을 가능성이 크다. 서버 로그로 반드시 관찰된다고 가정하지 않는다(5절).

## 2. 실제 SFA 인증 연계 (백엔드 단계)
| 항목 | 설계 |
|---|---|
| 접수자 | 서버가 인증 세션(SSO 등)에서 사용자 ID를 얻어 `submittedById`로 쓴다. 요청 본문의 접수자·지점 값은 무시한다 |
| 신고자 | 본인이면 접수자와 같다. 대리 접수면 요청의 `reporterId`를 받되, 서버가 "접수자 = 관리자, 신고자 = 같은 지점 FC"를 인사·조직 정보로 다시 확인한다(ADR-028 결정 2) |
| 이름·지점 | 저장하지 않고 조회한다. 조직 이동 이력이 필요하면 접수 시점의 지점 ID만 `Report.reporterBranchIdAtSubmit`로 남기는 것을 검토(이름은 남기지 않음) |
| 실패 | 세션이 없거나 조직 정보가 어긋나면 401/422로 거부하고 화면은 ADR-028의 검증 오류를 보인다 |

## 3. 추적 흐름과 최소 데이터
```
FC 계정(submittedById/reporterId) → 고객 동의 요청(consentRequestId) → 내부 추적 ID(traceId) → 관련 시스템 이벤트
```
- **내부 추적 ID(`traceId`)**: 업무 요청(예: 상품소개동의 요청)을 만들 때 업무 시스템이 발급하는 **임의 값**. 고객번호·주민등록번호·전화번호에서 만들지 않는다. URL에는 넣지 않거나, 넣더라도 추측할 수 없는 짧은 수명의 값이어야 한다.
- **신고에 붙일 값(후보)**: `Report.traceRefs: [{system: 'CONSENT', traceId, linkedBy, linkedAt}]`. FC가 직접 고르지 않고, IT 담당자가 신고자 계정·접수 시각으로 업무 시스템에서 찾아 **연결**한다(자동 연결 아님). 연결 기록(누가·언제)을 남긴다.
- **저장하지 않는 것**: 인증 토큰, 세션 쿠키, 전체 URL과 쿼리, 동의 URL의 서명값, 고객 식별정보, 업무 요청 전문(개인정보 포함), 운영 로그 원문.

### 고객 동의 URL 오류에서 볼 만한 이벤트(존재 여부 확인 필요)
| 순서 | 이벤트 | 기록 주체(예상) | 남길 값(최소) |
|---|---|---|---|
| 1 | 동의 요청 생성 | SFA·동의 시스템 | traceId, FC 계정, 상품군 코드, 시각 |
| 2 | URL 발송 | 발송 시스템 | traceId, 채널(문자·메신저), 결과 코드, 시각 |
| 3 | 고객 URL 접속 | 동의 웹 서버 | traceId, 기기 유형·브라우저 종류·주 버전(전체 User-Agent 아님), 시각 |
| 4 | 본인확인 입력 단계 진입 | 동의 웹(클라이언트) | traceId, 단계 코드(FRONT/BACK), 시각 — **입력값 없음** |
| 5 | 오류 진단 이벤트 | 동의 웹(클라이언트) | traceId, 진단 코드(예: 입력란 포커스 뒤 가상 키패드 미표시 추정), 시각 |

## 4. 운영 로그 조회와 접근 권한
- **조회 주체**: IT 담당자 역할만. 영업 담당은 결과 요약("관련 이벤트 n건 확인")만, FC·관리자는 보지 않는다.
- **조회 방식**: 결함 대장 ③ "로그 추적 단서"에 [로그 요청]을 두고, 실제 조회는 운영 시스템의 기존 권한·감사 체계 안에서 한다. 결함 대장은 요청 기록과 결과 요약(담당자가 적은 글)만 보관한다.
- **감사**: 누가 어떤 traceId를 언제 조회했는지 남긴다. 조회 사유(신고 ID) 필수.
- **보관 기간**: 신고에 연결한 traceId는 결함이 해결·종결된 뒤 정해진 기간(예: 90일, 정책 확인 필요)이 지나면 지운다. 로그 원문은 결함 대장에 복사하지 않는다.
- **최소화**: 결함 판단에 필요한 이벤트 종류·시각·결과 코드만 요약해 본다.

## 5. 고객 모바일 웹 진단 이벤트(가능성)
- 키패드 미표시는 기기·OS·브라우저의 입력 처리 문제일 수 있어 **서버 로그로는 보이지 않을 수 있다.** 확인하려면 동의 웹 페이지가 스스로 진단 이벤트를 보내야 한다.
- 후보 신호(개인정보 없이): 입력란 포커스 시각, `visualViewport` 높이 변화(가상 키패드가 올라오면 줄어듦) 여부, `inputmode`·`type` 속성 값, 기기 유형·브라우저 종류·주 버전, 앱 안 브라우저 여부(문자·메신저 앱 내장 여부).
- **보내지 않을 것**: 입력값, 입력 글자 수, 화면 캡처, 전체 User-Agent, 위치, 기기 고유 ID.
- 이 신호는 "키패드가 안 떴을 가능성"을 보여 줄 뿐 확정이 아니다. 실제 기기 재현으로 확인한다.
- 고객 동의(수집 고지)와 보안 검토가 먼저 필요하다.

## 6. 화면 확장 방향
- 결함 대장 ③ "로그 추적 단서"(ADR-028)의 "관련 업무 요청 식별자 · 연계 전"을 "연결된 traceId n건 · [로그 요청]"으로 바꾸고, 결과는 담당자가 적은 요약만 보인다.
- 신고 패널 ① "오류 발생 정보"에 모바일 진단 이벤트가 있으면 "진단 이벤트"(자동 확인) 줄을 FC 진술과 나란히 둔다(출처 구분 유지).
- FC 화면에는 traceId를 보이지 않는다.

## 7. 확인이 필요한 것
- 동의 요청·발송·접속 이벤트가 실제로 기록되는지, 보관 기간과 조회 권한 정책
- 업무 요청 식별자의 발급 주체와 형식(고객 식별정보에서 파생되지 않는지)
- 모바일 진단 이벤트 수집의 고지·동의·보안 검토
- 실제 담당 부서와 로그 요청 경로
