# 실제 업무 프로세스 기반 고도화 — 현황 분석과 변경 계획 (TASK 00)

- 상태: 검토 완료 (2026-11-25). ADR-030 승인과 사용자 선택(P0 먼저, SALES 재사용, 기존 코드 + 상위 업무)을 반영했다. 근거 지시서: "FC-VoC-Sys — 실제 업무 프로세스 기반 PoC 고도화 개발 지시서"
- 기준: `main` `874af77` (#26·#27·#28 반영). 단계 `FRONTEND`
- 관련 결정: [ADR-030](../adr/ADR-030-business-routing-handling-workflow.md)(승인)

## 1. 확인한 규칙과 전제
- **우선순위:** 승인된 ADR > `docs/00~12` > 지시서 > `proposal.md`. 지시서가 승인 ADR과 다른 곳은 ADR-030으로 바꾼 뒤에만 구현한다(4절).
- **단계:** `FRONTEND`. 바꿀 수 있는 곳은 `src/main/resources/static/**`, `docs/`, `scripts/`, `.claude/`다.
  - 지시서의 "API·데이터 모델"은 지금까지처럼 `api-client.js` + `js/fixtures/` + 같은 브라우저 저장소(`IntakeDemoStore`)로 구현한다.
  - 서버·DB·실제 LLM·실제 발송은 없다. "실제로 동작"은 이 시연 범위 안에서 역할을 바꿔도 이어진다는 뜻이다.
- **변경 순서:** ADR → 문서 → 구현 → 검사 → 디자인 리뷰(ADR-014).
- **원문 보관:** 자유 입력 원문은 페이지 메모리에만 둔다(ADR-021). 협의 결과·자체 해결 내용도 코드와 승인 문구로 저장하고, 자유 메모는 저장소에 넣지 않는다.
- **연결 주체:** 사람이 연결하고(ADR-017), AI·규칙은 후보만 낸다.

### 2-1. 실제 동작과 가상의 구분 (지금)
- **브라우저 안에서 실제로 동작:** 저장소 공유, 알림 기록·읽음, 상태 변경, 묶기, 업무 재개·현장 확인, 권한 검사.
- **고정 응답:** AI 문의 결과·비슷한 결함 추천(`fixtures`).
- **규칙:** 새 문의의 후보·등급·부서.
- **가상:** 진단 이벤트·검증 기록.
- **없음:** 실제 LLM·서버·발송·로그·ITGS.

## 3. 바꾸지 않는 것
- 대표 결함(공통 오류) 상태 7종과 전이 규칙(02번 3절), 검증 기록, 되돌림 규칙(ADR-029)
- 연결은 사람(ADR-017), 자유 입력 원문은 페이지 메모리(ADR-021), 신원 검증(ADR-028), 현장 확인은 신고자 본인 FC(ADR-029)
- S5 실험 경로: 숫자 단계 주소, `known=off`, A/B 모드, 측정 경계(09번). 새 첫 화면 선택지는 S5 주소에 나오지 않게 한다.
- 내부 코드·필드 이름(`Report`, `Defect`, `reporterId` 등)과 기존 주소 키. 화면 문구만 바꾼다.
- 기존 전자서명·고객 동의 시나리오와 회귀 검사(기대 문구만 새 용어로)

## 5. 변경 계획

### 5-1. 데이터 (모두 기존 저장 방식 안, 05번 1절에 추가)
| 영역 | 방식 |
|---|---|

| 문의함 `Inbox` | 부서 문의함(가상 부서), 공통 분류 문의함, 미분류 문의함 |
| 문의 분류 `Report.routing` | `{businessCode, parentCode, inboxId, basis[화면 ID·업무·증상·기존 이력], method: RULE, at}`. 재분류는 덧붙이기 이력 `routingHistory` |
| 담당 `Report.assignment` | `{assigneeId, at}` + 이력. 확인(`viewedBy`)·알림 읽음과 별도. 이미 인수된 문의는 인수 거부(`ALREADY_ASSIGNED`) |
| 대응 기록 `InquiryAction` | 덧붙이기: `INFO_REQUEST`(코드 항목) · `GUIDE`(승인된 공개 대응) · `SELF_RESOLVED`(적용 대응 코드) · `IT_CONSULT`(질문 코드·현업 확인 요약) · `IT_REPLY`(협의 결과 코드) · `REROUTE`. 문의 대응 상태는 마지막 기록에서 계산(새 상태 열 없음) |
| ITGS | 초안은 저장하지 않고 화면에서 만들어 복사만. 문서 번호·상태(진행중/반려종료/정상종료)를 적는 칸은 P1, 정상종료가 검증 완료를 뜻하지 않음 |

| 사용자 | 현업 담당자(`SALES` 역할 재사용 + `inboxIds`): 고객동의업무팀(가상) 2명(중복 인수 시연), 청약업무팀(가상) 1명, 공통 분류 담당 1명. 모두 "(가상)" |

### 5-2. API (`api-client.js`, 05번 3절에 추가)
- `classifyInquiry(req)`: 규칙 분류(후보·근거·문의함). 접수 저장 때 호출하고 결과를 그대로 저장
- `getInbox(userId, {filter})`: 내 문의함, 문의함 요약 수(신규·내 담당·추가 정보 필요·IT 협의 필요)
- `claimInquiry(reportId, userId, requestId)`, `rerouteInquiry(reportId, userId, inboxId, reasonCode)`
- `postInquiryAction(reportId, userId, action)`: 추가 정보 요청·대응 안내·자체 해결·IT 협의 요청·협의 결과
- `getItConsults(userId)`, `getItgsDraft(reportId, userId)`
- 권한: 문의함 담당자·IT는 그 범위, 관리자는 같은 지점 FC, FC는 본인. 범위 밖 상세는 거부

### 5-3. 화면
- **현업 담당자:** 결함 대장 화면(`ledger.html`)을 "전산 문의 관리"로 바꾸고 첫 탭을 [전산 문의함]으로 한다.
